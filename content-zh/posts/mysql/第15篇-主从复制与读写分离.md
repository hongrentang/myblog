## 什么是主从复制？

主从复制是将主数据库（Master）的数据变更同步到从数据库（Slave）的过程。

```
主库（Master）→ binlog → 从库（Slave）→ relay log → 数据变更
```

**主从复制的作用：**

| 作用 | 说明 |
|------|------|
| 读写分离 | 主库写，从库读，分摊压力 |
| 数据备份 | 从库可以作为实时备份 |
| 高可用 | 主库挂了可以切换从库 |
| 数据分析 | BI/报表查询在从库执行，不影响主库 |

---

## 一、复制原理

```
主库
┌──────────────────────┐
│ 1. 事务提交 → 写入   │  binlog
│    binlog            │───────┐
└──────────────────────┘       │
                               │
                        从库 IO 线程
                               │
                          ┌────┴─────────┐
                          │ 2. 拉取 binlog  │
                          │    写入 relay log│
                          └────┬─────────┘
                               │
                        从库 SQL 线程
                               │
                          ┌────┴─────────┐
                          │ 3. 回放 relay  │
                          │    log 到本地   │
                          └──────────────┘
```

### 三个线程

| 线程 | 位置 | 作用 |
|------|------|------|
| Binlog dump 线程 | 主库 | 发送 binlog 给从库 |
| IO 线程 | 从库 | 接收 binlog 并写入 relay log |
| SQL 线程 | 从库 | 读取 relay log 并回放 |

## 二、配置主从复制

### 主库配置

```ini
# my.cnf（主库）
[mysqld]
server-id = 1                    # 唯一 ID（主从不能重复）
log_bin = /var/log/mysql/mysql-bin.log
binlog_format = ROW              # ROW 格式最安全
binlog_row_image = FULL
expire_logs_days = 7
# 如果要复制指定数据库
# binlog-do-db = shop
# binlog-ignore-db = mysql
```

```bash
# 重启主库
sudo systemctl restart mysql
```

### 创建复制用户

```sql
-- 登录主库
CREATE USER 'repl'@'192.168.1.%' IDENTIFIED BY 'repl_password_123!';
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'repl'@'192.168.1.%';
FLUSH PRIVILEGES;

-- 查看主库状态（记录下 File 和 Position）
SHOW MASTER STATUS;
+------------------+----------+--------------+------------------+
| File             | Position | Binlog_Do_DB | Binlog_Ignore_DB |
+------------------+----------+--------------+------------------+
| mysql-bin.000003 |     1234 |              |                  |
+------------------+----------+--------------+------------------+
```

### 从库配置

```ini
# my.cnf（从库）
[mysqld]
server-id = 2                    # 必须与主库不同
log_bin = /var/log/mysql/mysql-bin.log  # 从库也可以开启 binlog
relay_log = /var/log/mysql/mysql-relay-bin.log
read_only = 1                    # 从库只读（防止误写入）
relay_log_recovery = 1           # relay log 崩溃恢复
```

```bash
sudo systemctl restart mysql
```

### 启动复制

```sql
-- 登录从库
CHANGE MASTER TO
    MASTER_HOST = '192.168.1.100',
    MASTER_PORT = 3306,
    MASTER_USER = 'repl',
    MASTER_PASSWORD = 'repl_password_123!',
    MASTER_LOG_FILE = 'mysql-bin.000003',
    MASTER_LOG_POS = 1234,
    MASTER_CONNECT_RETRY = 10,
    MASTER_RETRY_COUNT = 0;

-- 启动复制
START SLAVE;

-- 查看复制状态
SHOW SLAVE STATUS\G
```

### 验证复制状态

```sql
SHOW SLAVE STATUS\G
```

关键字段：

```
Slave_IO_State: Waiting for master to send event     -- IO 线程状态
Slave_IO_Running: Yes                                 -- IO 线程在运行
Slave_SQL_Running: Yes                                -- SQL 线程在运行
Seconds_Behind_Master: 0                              -- 延迟秒数（为 0 最好）
Last_IO_Errno: 0                                      -- IO 线程错误码
Last_SQL_Errno: 0                                     -- SQL 线程错误码
```

**正常状态**：
- `Slave_IO_Running: Yes`
- `Slave_SQL_Running: Yes`
- `Seconds_Behind_Master: 0`（理想状态，允许短暂不为 0）

## 三、GTID 复制（MySQL 5.6+）

GTID（Global Transaction Identifier）是每笔事务的全局唯一 ID，简化了主从切换和故障恢复。

### 开启 GTID

```ini
# my.cnf（主库和从库都要配置）
[mysqld]
gtid_mode = ON
enforce_gtid_consistency = ON
```

### GTID 方式配置复制

```sql
-- 从库上配置
CHANGE MASTER TO
    MASTER_HOST = '192.168.1.100',
    MASTER_PORT = 3306,
    MASTER_USER = 'repl',
    MASTER_PASSWORD = 'repl_password_123!',
    MASTER_AUTO_POSITION = 1;  -- 使用 GTID 自动定位

START SLAVE;
```

GTID 复制的优势：
- 不需要手动指定 `MASTER_LOG_FILE` 和 `MASTER_LOG_POS`
- 主从切换时，新主库的 GTID 集合会自动传递给新从库
- 复制中断后，自动通过 GTID 跳过已执行的事务

## 四、半同步复制

默认的异步复制中，主库提交事务后立即返回客户端，不等待从库确认。如果主库突然宕机，已提交的事务可能还没同步到从库。

**半同步复制**：主库等待至少一个从库确认收到 binlog 后才提交。

```sql
-- 安装插件（主库和从库）
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';
INSTALL PLUGIN rpl_semi_sync_slave SONAME 'semisync_slave.so';

-- 主库启用
SET GLOBAL rpl_semi_sync_master_enabled = 1;
SET GLOBAL rpl_semi_sync_master_timeout = 5000;  -- 5 秒超时（超时后降级为异步）

-- 从库启用
SET GLOBAL rpl_semi_sync_slave_enabled = 1;

-- 重启复制
STOP SLAVE IO_THREAD;
START SLAVE IO_THREAD;
```

### 永久配置

```ini
# my.cnf（主库）
[mysqld]
rpl_semi_sync_master_enabled = 1
rpl_semi_sync_master_timeout = 5000

# my.cnf（从库）
rpl_semi_sync_slave_enabled = 1
```

## 五、读写分离

配置好主从复制后，需要在应用层实现读写分离。

### 应用层实现（推荐）

```python
# Python 示例（使用 SQLAlchemy）

from sqlalchemy import create_engine
from sqlalchemy.orm import Session

# 主库（写）
master_engine = create_engine('mysql://user:pass@192.168.1.100:3306/shop')
# 从库（读）
slave_engine = create_engine('mysql://user:pass@192.168.1.101:3306/shop')

def get_db(read_only=False):
    if read_only:
        return Session(bind=slave_engine)
    return Session(bind=master_engine)

# 使用
db = get_db(read_only=True)    # 查询走从库
users = db.query(User).all()

db = get_db(read_only=False)   # 写入走主库
db.add(new_user)
db.commit()
```

### ProxySQL 中间件

```bash
# 安装 ProxySQL
sudo apt install proxysql
sudo systemctl start proxysql
```

```sql
-- 配置 ProxySQL（通过管理接口 6032 端口）
mysql -u admin -padmin -h 127.0.0.1 -P 6032

-- 添加后端服务器
INSERT INTO mysql_servers (hostgroup_id, hostname, port) VALUES
    (0, '192.168.1.100', 3306),  -- 主库（写）
    (1, '192.168.1.101', 3306),  -- 从库1（读）
    (1, '192.168.1.102', 3306);  -- 从库2（读）

-- 配置读写分离规则
INSERT INTO mysql_query_rules
    (rule_id, active, match_pattern, destination_hostgroup, apply)
VALUES
    (1, 1, '^SELECT.*', 1, 1),          -- SELECT 走从库
    (2, 1, '^INSERT|UPDATE|DELETE.*', 0, 1),  -- 写入走主库
    (3, 1, '^SELECT.*FOR UPDATE', 0, 1);      -- FOR UPDATE 走主库

-- 加载配置
LOAD MYSQL SERVERS TO RUNTIME;
SAVE MYSQL SERVERS TO DISK;
LOAD MYSQL QUERY RULES TO RUNTIME;
SAVE MYSQL QUERY RULES TO DISK;
```

## 六、常见问题与处理

### 复制中断

**错误类型 1：SQL 线程报错**

```sql
-- 查看错误
SHOW SLAVE STATUS\G
-- Last_SQL_Error: Could not execute ...  # 通常是主从数据不一致

-- 跳过指定数量的错误（应急）
STOP SLAVE;
SET GLOBAL sql_slave_skip_counter = 1;
START SLAVE;

-- 或者跳过指定错误类型
-- 在 my.cnf 中设置：
-- slave_skip_errors = 1062  # 跳过主键重复
-- slave_skip_errors = 1032  # 跳过找不到记录的更新/删除
```

更好的做法：找到不一致的数据并修复，而不是直接跳过。

**错误类型 2：IO 线程报错**

```
Last_IO_Error: error reconnecting to master
```

检查：
1. 主库是否可达
2. 复制用户密码是否正确
3. 主库 binlog 是否已被清理

### 主从延迟

```sql
-- 查看延迟
SHOW SLAVE STATUS\G
-- Seconds_Behind_Master: 120  -- 延迟 120 秒
```

延迟常见原因：

| 原因 | 解决方案 |
|------|---------|
| 从库配置低 | 升级从库硬件 |
| 主库大事务 | 拆分为小事务 |
| 从库执行慢查询 | 优化从库查询 |
| 网络延迟 | 主从部署在同一机房 |

### 主从切换

```sql
-- 将从库提升为主库
STOP SLAVE;
RESET SLAVE ALL;
-- 此时从库变为独立的主库

-- 如果使用 GTID，切换特别简单
-- 原从库直接接受写操作即可
```

## 七、一主多从与主主复制

### 一主多从架构

```
              主库
            /  |  \
          从库 从库 从库
```

可以做到一主三从、一主五从甚至更多。从库越多，读能力越强，但主库需要复制到所有从库的 IO 压力也越大。

### 主主复制（双向复制）

两个库互为主从，任何一方的写入都会同步到另一方。

**不推荐在一般场景使用**——容易产生数据冲突（如两边同时 INSERT 同一主键）。适合特殊场景如异地多活。

---

## 八、复制架构推荐

### 单主多从 + 读写分离（推荐）

```
应用 → ProxySQL
       ├─ 主库（写）
       └─ 从库1（读）
       └─ 从库2（读）
       └─ 从库3（备份/报表）
```

### 级联复制

```
主库 → 从库1 → 从库2 → 从库3
```

减少主库的复制压力，从库1既是从库也是其他从库的主库。适合从库数量较多的场景。
