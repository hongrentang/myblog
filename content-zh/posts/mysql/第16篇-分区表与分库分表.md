## 什么时候需要分区/分表？

```
数据量
├── 百万级 → 合理索引即可
├── 千万级 → 分区表（单个 MySQL 实例）
├── 亿级   → 分库分表（多个 MySQL 实例）
└── 十亿+  → 分布式数据库（TiDB、OceanBase）
```

---

## 一、分区表（表内分区）

分区是将一张大表按规则拆分为多个物理子表，但对应用层透明（看起来仍是一张表）。

### 分区类型

#### 1. RANGE 分区（按范围）

```sql
-- 按订单年份分区
CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT,
    order_no VARCHAR(32),
    total_amount DECIMAL(10,2),
    created_at DATETIME,
    PRIMARY KEY (id, created_at)  -- 分区列必须包含在主键中
) PARTITION BY RANGE (YEAR(created_at)) (
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
```

#### 2. LIST 分区（按离散值列表）

```sql
-- 按地区分区
CREATE TABLE users (
    id INT,
    name VARCHAR(50),
    region VARCHAR(10),
    PRIMARY KEY (id, region)
) PARTITION BY LIST COLUMNS(region) (
    PARTITION p_north VALUES IN ('北京', '天津', '河北'),
    PARTITION p_east VALUES IN ('上海', '江苏', '浙江'),
    PARTITION p_south VALUES IN ('广东', '深圳', '福建')
);
```

#### 3. HASH 分区（按哈希值）

```sql
-- 按用户 ID 平均分布到 8 个分区
CREATE TABLE user_logs (
    id BIGINT,
    user_id INT,
    action VARCHAR(50),
    created_at DATETIME,
    PRIMARY KEY (id, user_id)
) PARTITION BY HASH(user_id) PARTITIONS 8;
```

#### 4. KEY 分区（类似 HASH，使用 MySQL 内置哈希函数）

```sql
CREATE TABLE sessions (
    id INT PRIMARY KEY,
    session_id VARCHAR(64),
    data TEXT
) PARTITION BY KEY(session_id) PARTITIONS 10;
```

### 分区查询优化

```sql
-- 查询时显式指定分区（分区裁剪）
SELECT * FROM orders PARTITION (p2024);

-- EXPLAIN 查看是否使用了分区裁剪
EXPLAIN SELECT * FROM orders WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31';
-- 如果 type 是 ALL 但 partitions 只显示了 p2024，说明做了分区裁剪
```

### 分区管理

```sql
-- 添加分区
ALTER TABLE orders ADD PARTITION (
    PARTITION p2026 VALUES LESS THAN (2027)
);

-- 删除分区（分区级别的快速删除）
ALTER TABLE orders DROP PARTITION p2023;

-- 拆分分区
ALTER TABLE orders REORGANIZE PARTITION p_future INTO (
    PARTITION p2026 VALUES LESS THAN (2027),
    PARTITION p2027 VALUES LESS THAN (2028),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);

-- 查看分区信息
SELECT
    PARTITION_NAME,
    PARTITION_METHOD,
    PARTITION_EXPRESSION,
    TABLE_ROWS
FROM information_schema.PARTITIONS
WHERE TABLE_SCHEMA = 'shop' AND TABLE_NAME = 'orders';
```

### 分区的注意事项

```sql
-- ❌ 分区列必须包含在主键或唯一索引中
CREATE TABLE bad (
    id INT PRIMARY KEY,
    created_at DATE
) PARTITION BY RANGE (YEAR(created_at)) (
    PARTITION p1 VALUES LESS THAN (2025)
);
-- 报错：A PRIMARY KEY must include all columns in the table's partitioning function

-- ✅ 复合主键包含分区列
CREATE TABLE good (
    id INT,
    created_at DATE,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (YEAR(created_at)) (
    PARTITION p1 VALUES LESS THAN (2025)
);
```

### 分区适用场景

| ✅ 适合 | ❌ 不适合 |
|---------|----------|
| 按时间归档的大表 | 关联查询频繁的表 |
| 按地区/类别分组的数据 | 需要唯一主键且无法包含分区列 |
| 需要快速按时间范围删除历史数据 | 分区数过多的表（建议 ≤ 1024）|
| 历史数据很少修改的表 | 经常跨分区查询的场景 |

**一句话总结：分区相当于给表加了物理层面的"抽屉"，适合按时间归档的场景。**

## 二、分库分表（多实例）

当单表数据超过千万甚至亿级，单个 MySQL 实例已经无法承载时，就需要**分库分表**。

### 垂直分表

按业务字段拆分：

```sql
-- 原表：字段太多，一次查询不需要全部
users (
    id, name, email, phone, password_hash,
    avatar, bio, address, created_at, updated_at,
    login_ip, login_count, last_login_at  -- 不常查询
)

-- 拆分为：
users_base (id, name, email, phone, avatar, created_at)
users_auth (user_id, password_hash, login_ip, login_count, last_login_at)
```

### 水平分表

按某个键将数据分散到多张结构相同的表：

```sql
-- 按 user_id 分 16 张表
user_0, user_1, user_2, ..., user_15

-- 路由规则：
table_index = user_id % 16

-- 查询：
SELECT * FROM user_${user_id % 16} WHERE user_id = 100;
```

### 水平分库

将表分散到不同的 MySQL 实例：

```sql
-- 按 user_id 分摊到 4 个数据库
db0: user_0 ~ user_3
db1: user_4 ~ user_7
db2: user_8 ~ user_11
db3: user_12 ~ user_15

-- 路由：
db_index = user_id % 4
table_index = (user_id / 4) % 4
```

## 三、分片中间件

### ShardingSphere（推荐）

```yaml
# ShardingSphere-JDBC 配置示例
spring:
  shardingsphere:
    datasource:
      names: ds0, ds1
      ds0:
        url: jdbc:mysql://192.168.1.100:3306/shop0
        username: app
        password: pass
      ds1:
        url: jdbc:mysql://192.168.1.101:3306/shop1
        username: app
        password: pass

    sharding:
      tables:
        users:
          actual-data-nodes: ds$->{0..1}.users_$->{0..1}
          table-strategy:
            standard:
              sharding-column: user_id
              sharding-algorithm-name: user-table-inline
          database-strategy:
            standard:
              sharding-column: user_id
              sharding-algorithm-name: user-db-inline
          key-generator:
            column: id
            type: SNOWFLAKE

    sharding-algorithms:
      user-db-inline:
        type: INLINE
        props:
          algorithm-expression: ds$->{user_id % 2}
      user-table-inline:
        type: INLINE
        props:
          algorithm-expression: users_$->{user_id % 2}
```

## 四、分片策略

### 取模分片

```sql
-- 最简单，但扩缩容需要迁移数据
db_index = user_id % 4
```

### 哈希分片

```sql
-- 适合不是数字的主键
db_index = CRC32(order_no) % 8
```

### 范围分片

```sql
-- 按 ID 范围，扩容方便
db0: user_id 1 ~ 10000000
db1: user_id 10000001 ~ 20000000
```

### 一致性哈希

减少扩缩容时的数据迁移量，适合频繁变动的集群。

## 五、分库分表带来的问题

| 问题 | 说明 | 解决方案 |
|------|------|---------|
| 跨分片查询 | 聚合查询需要在多个分片执行后汇总 | 避免或少用跨分片操作 |
| 分布式事务 | 跨库操作的一致性 | Seata、TCC、最终一致性 |
| 全局主键 | 自增主键会重复 | Snowflake、UUID（推荐有序 UUID v7）|
| 跨分片排序 | 需要各分片排序后再合并 | 中间件支持，但尽量缩小结果集 |
| 关联查询 | 多表 JOIN 变困难 | 冗余字段、应用层组装 |

### 全局主键生成

```java
// Snowflake ID 生成（Java 示例）
public class SnowflakeIdWorker {
    private long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("Clock moved backwards");
        }
        if (lastTimestamp == timestamp) {
            sequence = (sequence + 1) & 4095;
            if (sequence == 0) {
                timestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0;
        }
        lastTimestamp = timestamp;
        return ((timestamp - 1288834974657L) << 22)
             | (workerId << 12)
             | sequence;
    }
}
```

## 六、架构演进路径

```sql
-- 第一阶段：单库单表
单实例 MySQL

-- 第二阶段：读写分离
主库（写）+ 从库（读）

-- 第三阶段：分库分表
多个 MySQL 实例 + 中间件

-- 第四阶段：分布式数据库
TiDB / OceanBase / PolarDB
```

**什么时候需要走到分库分表？**

```
1. 数据量 > 单表 5000 万行或 > 100GB
2. MySQL 写入成为瓶颈（单库无法承载写入 QPS）
3. 单库连接数不够用
4. 按业务拆分多个库更合理
```

**没到上述阈值之前，先做好索引、分区、读写分离，不要盲目分库分表。**

## 七、分区 vs 分库分表 对比

| 对比 | 分区 | 分库分表 |
|------|------|---------|
| 复杂度 | 低（配置简单）| 高（需要中间件）|
| 对应用透明 | ✅ 完全透明 | ❌ 需要改造 |
| 跨分片查询 | ✅ 自动支持 | ❌ 受限 |
| 事务 | ✅ 支持 | ❌ 分布式事务 |
| 扩展性 | 受限于单实例 | ✅ 可无限扩展 |
| 适用数据量 | 千万 ~ 亿级 | 亿级 + |
