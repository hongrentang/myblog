## 为什么需要索引？

没有索引的查询叫 **全表扫描**——MySQL 需要从头到尾读整张表。索引相当于书的目录，通过目录快速定位到内容所在位置。

```
全表扫描：翻遍整本书找一页内容
索引查找：查目录 → 直接翻到那一页
```

---

## 一、索引数据结构：B+ Tree

MySQL InnoDB 使用 **B+ Tree** 作为索引结构。

```
                  [根节点]
              /      |      \
         [分支]   [分支]   [分支]
         /   \    /   \    /   \
      [叶子] [叶子][叶子][叶子][叶子]
       数据   数据  数据   数据  数据
```

### B+ Tree 特点

| 特性 | 说明 |
|------|------|
| 多路平衡树 | 每个节点可存储多个 key，树的高度很低 |
| 叶子节点存数据 | 所有数据都在叶子节点 |
| 叶子节点有链表 | 方便范围查询（>、<、BETWEEN）|
| 非叶子节点只存 key | 不存数据，一页能装更多 key |

### 查询次数

InnoDB 的 B+ Tree 高度通常是 **2~4 层**（百万级数据 3 层足够）。查询一次索引 = 读取 2~4 次磁盘页，相对于全表扫描是数量级的提升。

## 二、聚簇索引 vs 二级索引

### 聚簇索引（Clustered Index）

InnoDB 中，**主键就是聚簇索引**。叶子节点直接存储整行数据。

```
聚簇索引（主键 id）
[1: 张三...] → [2: 李四...] → [3: 王五...] → ...
```

- 每个表有且只有一个聚簇索引
- 如果没有定义主键，InnoDB 会选第一个 UNIQUE 列作为聚簇索引
- 都没有的话，InnoDB 自动生成隐藏的 ROW_ID

### 二级索引（Secondary Index）

非主键索引都是二级索引。叶子节点存储的是**主键值**。

```
二级索引（name）
[张三: 1] → [李四: 2] → [王五: 3] → ...
```

### 回表查询

```sql
CREATE INDEX idx_name ON users(name);

-- 查询过程（回表）：
SELECT * FROM users WHERE name = '张三';
-- 1. 通过 idx_name 找到主键 id = 1
-- 2. 通过主键 id = 1 回聚簇索引找到整行数据
```

### 覆盖索引

如果查询的字段都在二级索引里，就不需要回表：

```sql
-- 只需要 name 和 id，idx_name 已经包含 → 无需回表
SELECT id, name FROM users WHERE name = '张三';
```

## 三、索引类型

### 普通索引

```sql
CREATE INDEX idx_email ON users(email);
```

### 唯一索引

```sql
CREATE UNIQUE INDEX idx_email ON users(email);
-- 比普通索引多一层唯一性约束，对查询来说与普通索引性能相近
```

### 联合索引

```sql
CREATE INDEX idx_name_age ON users(name, age);
```

**最左前缀原则**：

```sql
idx_name_age(name, age)

-- ✅ 走索引
WHERE name = '张三'
WHERE name = '张三' AND age = 25
WHERE name LIKE '张%'

-- ❌ 不走索引（跳过了 name）
WHERE age = 25
WHERE age > 20 AND name = '张三'  -- 只用到 name 部分
```

### 前缀索引

```sql
-- 对字符串的前 N 个字符建索引，节省空间
CREATE INDEX idx_email_prefix ON users(email(10));
```

### 全文索引

```sql
CREATE FULLTEXT INDEX idx_content ON articles(content);

-- 使用 MATCH ... AGAINST 查询
SELECT * FROM articles
WHERE MATCH(content) AGAINST('数据库优化' IN BOOLEAN MODE);
```

## 四、索引优化实战

### 1. 选择索引列

```sql
-- ✅ 适合建索引的列
WHERE status = 1           -- 过滤性高
WHERE user_id = 100        -- 经常出现在 WHERE 中
ORDER BY created_at        -- 经常排序
JOIN ... ON a.user_id = b.id  -- JOIN 关联列

-- ❌ 不适合建索引的列
gender                     -- 只有 '男'/'女'，过滤性太差
content                    -- 太大，用前缀索引或全文索引
```

### 2. EXPLAIN 分析索引使用

```sql
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
```

| 列 | 说明 | 好 | 差 |
|----|------|----|----|
| `type` | 访问类型 | const/ref/range | ALL |
| `possible_keys` | 可能使用的索引 | 有值 | NULL |
| `key` | 实际使用的索引 | 有值 | NULL |
| `rows` | 扫描行数 | 小 | 大（百万级）|
| `Extra` | 额外信息 | Using index | Using filesort |

**type 从好到差**：

```
system > const > eq_ref > ref > range > index > ALL
```

- `const`：主键或唯一索引等值查询（最快）
- `ref`：普通索引等值查询
- `range`：范围查询
- `index`：扫描了整棵索引树
- `ALL`：全表扫描（最差）

### 3. 常见索引问题

```sql
-- ❌ 索引列上有函数运算（索引失效）
WHERE DATE(created_at) = '2025-01-15'
-- ✅ 改为范围查询
WHERE created_at >= '2025-01-15' AND created_at < '2025-01-16'

-- ❌ 隐式类型转换（索引失效）
WHERE phone = 13800138000  -- phone 是 VARCHAR
-- ✅ 显式用字符串
WHERE phone = '13800138000'

-- ❌ LIKE 以 % 开头（索引失效）
WHERE name LIKE '%张'
-- ✅ 不以 % 开头
WHERE name LIKE '张%'

-- ❌ OR 两边只有一个有索引（索引失效）
WHERE email = 'test@test.com' OR name = '张三'
-- ✅ 改为 UNION
SELECT * FROM users WHERE email = 'test@test.com'
UNION
SELECT * FROM users WHERE name = '张三'

-- ❌ != 或 NOT IN（通常不走索引）
WHERE status != 1
```

### 4. 索引维护

```sql
-- 查看索引使用情况
SELECT
    index_name,
    cardinality,
    (cardinality / (SELECT COUNT(*) FROM users)) * 100 AS selectivity
FROM information_schema.statistics
WHERE table_schema = 'shop' AND table_name = 'users';

-- 分析表（更新统计信息）
ANALYZE TABLE users;

-- 查看索引大小
SELECT
    database_name,
    table_name,
    index_name,
    ROUND(stat_value * @@innodb_page_size / 1024 / 1024, 2) AS size_mb
FROM mysql.innodb_index_stats
WHERE stat_name = 'size' AND table_name = 'users';
```

## 五、索引设计原则

```
索引设计检查清单：
□ 主键：自增 BIGINT（保证插入顺序，减少页分裂）
□ WHERE 频繁使用的列
□ JOIN 关联列（两边类型一致）
□ ORDER BY 列（减少 filesort）
□ 高选择性列先放（唯一值多的在前面）
□ 控制索引数量（单表不超过 5~8 个）
□ 大字段用前缀索引
□ 不要给每个列都建索引
```

### 索引数量权衡

| 索引多 | 索引少 |
|--------|--------|
| 查询快 | 写入快 |
| 插入/更新慢 | 插入/更新快 |
| 占用磁盘多 | 占用磁盘少 |

**核心原则**：索引是为了加速查询而建的，不要为不常用的查询建索引。

## 六、复合索引最左前缀详解

```sql
-- 建一个复合索引：(a, b, c)
CREATE INDEX idx_a_b_c ON t(a, b, c);

-- 走索引的查询
WHERE a = 1                          -- ✅ a
WHERE a = 1 AND b = 2                -- ✅ a, b
WHERE a = 1 AND b = 2 AND c = 3      -- ✅ a, b, c
WHERE a = 1 AND c = 3                -- ✅ a（但只用到了 a，c 没用到）
WHERE b = 2                          -- ❌ 不走索引

-- 范围查询后的列不走索引
WHERE a = 1 AND b > 10 AND c = 3     -- ✅ a, b（c 不走索引，因为 b 是范围）
```

## 七、MRR 与 ICP 优化

### Index Condition Pushdown（ICP）

```sql
-- MySQL 5.6+ 默认启用，将 WHERE 条件下推到索引层过滤
-- 没有 ICP：回表后再过滤
-- 有 ICP：在索引层先过滤，减少回表次数
SET optimizer_switch = 'index_condition_pushdown=on';
```

### Multi-Range Read（MRR）

```sql
-- 回表前先按主键排序，变随机 I/O 为顺序 I/O
SET optimizer_switch = 'mrr=on,mrr_cost_based=on';
```

## 八、实战索引优化案例

```sql
-- 原始查询（慢）
SELECT * FROM orders
WHERE user_id = 100 AND status = 1
ORDER BY created_at DESC
LIMIT 10;

-- 分析
EXPLAIN 会看到 type: ref（user_id）但 Extra: Using filesort

-- 优化方案1：建复合索引
CREATE INDEX idx_user_status_time ON orders(user_id, status, created_at DESC);
-- 索引顺序与 WHERE + ORDER BY 匹配，全部走索引

-- 优化方案2：如果只有 user_id 会查很多记录，先缩小范围
CREATE INDEX idx_user_time ON orders(user_id, created_at DESC);
```
