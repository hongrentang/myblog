## 性能优化的总体思路

```
定位问题 → 分析原因 → 制定方案 → 实施优化 → 验证效果
```

MySQL 性能优化通常从三个层面展开：

1. **查询层面**：SQL 语句是否高效
2. **索引层面**：索引设计是否合理
3. **配置层面**：MySQL 参数是否适配硬件

---

## 一、慢查询日志

慢查询日志是性能优化的**第一入口**。

### 开启慢查询日志

```sql
-- 查看当前慢查询配置
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';

-- 开启（临时）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;        -- 超过 1 秒的记录
SET GLOBAL log_queries_not_using_indexes = ON;  -- 记录未使用索引的查询

-- 永久开启（my.cnf）
slow_query_log = ON
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 1
log_queries_not_using_indexes = ON
```

### 查看慢查询

```sql
-- 查看慢查询数量
SHOW GLOBAL STATUS LIKE 'Slow_queries';

-- 查看当前有多少慢查询
SELECT COUNT(*) FROM mysql.slow_log;
```

### mysqldumpslow 分析

```bash
# 按执行次数排序
mysqldumpslow -s c /var/log/mysql/slow.log

# 按平均查询时间排序（最常用）
mysqldumpslow -s t /var/log/mysql/slow.log

# 只查看 top 10
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log

# 按锁等待时间排序
mysqldumpslow -s l /var/log/mysql/slow.log

# 输出详细信息
mysqldumpslow -a -s t -t 5 /var/log/mysql/slow.log
```

### pt-query-digest（Percona Toolkit）

```bash
# 安装
sudo apt install percona-toolkit

# 分析慢查询
pt-query-digest /var/log/mysql/slow.log

# 分析结果输出到文件
pt-query-digest /var/log/mysql/slow.log > slow_query_report.txt

# 分析实时 MySQL 查询
pt-query-digest --processlist mysql://user@localhost
```

## 二、EXPLAIN 执行计划

EXPLAIN 是分析单个查询的利器。

### 基本用法

```sql
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';

-- MySQL 8.0.16+ 支持 EXPLAIN ANALYZE（输出实际执行时间）
EXPLAIN ANALYZE SELECT * FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.email = 'test@example.com';
```

### 输出解读

| 列 | 含义 | 好 | 差 |
|----|------|----|----|
| `id` | 查询中 SELECT 的序号 | 简单查询 id = 1 | — |
| `select_type` | 查询类型 | SIMPLE | SUBQUERY、DERIVED |
| `table` | 表名 | — | — |
| `type` | 访问类型 | const/eq_ref/ref/range | ALL（全表扫）|
| `possible_keys` | 可能使用的索引 | 有值 | NULL |
| `key` | 实际使用的索引 | 有值 | NULL |
| `key_len` | 使用的索引长度 | 合理范围 | 过大或过小 |
| `ref` | 索引使用的列或常量 | 有值 | NULL |
| `rows` | 预估扫描行数 | 小 | 大 |
| `filtered` | 经过 WHERE 过滤后的百分比 | 100 | 小 |
| `Extra` | 额外信息 | Using index | Using filesort、Using temporary |

### type 从好到差

```
system > const > eq_ref > ref > fulltext > ref_or_null
  > index_merge > unique_subquery > index_subquery
  > range > index > ALL
```

重点关注红色标记：
- **`ALL`**：全表扫描，通常需要优化
- **`index`**：索引全扫描（还是会扫所有索引行，不一定差但需审视）
- **`Using filesort`**：需要额外的排序操作
- **`Using temporary`**：使用了临时表（通常是 GROUP BY 或 DISTINCT）

### EXPLAIN ANALYZE 示例

```sql
EXPLAIN ANALYZE
SELECT u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.created_at > '2025-01-01'
GROUP BY u.id;
```

输出示例：

```
-> Group aggregate: count(o.id)  (cost=5234 rows=1234)
   -> Left hash join (o.user_id = u.id)  (cost=4123 rows=12345)
      -> Filter: (u.created_at > TIMESTAMP '2025-01-01')  (cost=123 rows=500)
         -> Table scan on u  (cost=123 rows=1000)
      -> Hash
         -> Index scan on o using idx_user_id  (cost=2000 rows=10000)
```

执行计划会显示每一步的实际耗时，帮你找到瓶颈。

## 三、Performance Schema

MySQL 5.7+ 自带的性能监控工具。

### 启用 Performance Schema

```sql
-- 查看是否启用
SHOW VARIABLES LIKE 'performance_schema';

-- 在 my.cnf 中启用
-- performance_schema = ON
```

### 常用查询

```sql
-- 1. 查看最耗时的 SQL 语句（按总执行时间排）
SELECT
    digest_text AS query,
    count_star AS exec_count,
    sum_timer_wait / 1000000000000 AS total_time_sec,
    avg_timer_wait / 1000000000000 AS avg_time_sec,
    sum_rows_examined / count_star AS avg_rows_examined
FROM performance_schema.events_statements_summary_by_digest
WHERE schema_name = 'shop'
ORDER BY sum_timer_wait DESC
LIMIT 10;

-- 2. 查看 IO 压力最大的表
SELECT
    object_schema,
    object_name,
    count_read,
    count_write,
    count_fetch,
    sum_timer_read / 1000000000000 AS read_time_sec
FROM performance_schema.table_io_waits_summary_by_table
ORDER BY sum_timer_read DESC
LIMIT 10;

-- 3. 查看锁等待情况
SELECT
    object_schema,
    object_name,
    index_name,
    count_star,
    count_read,
    count_insert,
    count_update,
    count_delete
FROM performance_schema.table_lock_waits_summary_by_table
ORDER BY count_star DESC
LIMIT 10;
```

## 五、监控关键指标

### 系统状态

```sql
-- 查看 MySQL 运行状态
SHOW GLOBAL STATUS;

-- 关键指标
-- 连接数
SHOW GLOBAL STATUS LIKE 'Threads_%';

-- QPS（每秒查询数）
SHOW GLOBAL STATUS LIKE 'Queries';

-- TPS（每秒事务数）
SHOW GLOBAL STATUS LIKE 'Com_commit';
SHOW GLOBAL STATUS LIKE 'Com_rollback';

-- 缓冲池命中率
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
```

### 计算关键指标

```sql
-- 计算缓存命中率
SELECT
    (1 - (
        SELECT VARIABLE_VALUE FROM performance_schema.global_status
        WHERE VARIABLE_NAME = 'Innodb_buffer_pool_reads'
    ) / (
        SELECT VARIABLE_VALUE FROM performance_schema.global_status
        WHERE VARIABLE_NAME = 'Innodb_buffer_pool_read_requests'
    )) * 100 AS buffer_pool_hit_rate;

-- 计算 QPS
SELECT
    (VARIABLE_VALUE - @last_queries) / 10 AS qps
FROM performance_schema.global_status
WHERE VARIABLE_NAME = 'Queries';
```

## 六、InnoDB 引擎监控

```sql
-- 查看 InnoDB 状态（很多关键信息）
SHOW ENGINE INNODB STATUS\G

-- 关键关注点：
-- 1. LATEST DETECTED DEADLOCK（最近死锁）
-- 2. TRANSACTIONS（当前活跃事务）
-- 3. BUFFER POOL AND MEMORY（缓冲池使用）
-- 4. ROW OPERATIONS（行操作统计）

-- 查看数据表大小
SELECT
    table_name,
    ROUND((data_length + index_length) / 1024 / 1024, 2) AS total_mb,
    ROUND(data_length / 1024 / 1024, 2) AS data_mb,
    ROUND(index_length / 1024 / 1024, 2) AS index_mb,
    table_rows
FROM information_schema.tables
WHERE table_schema = 'shop'
ORDER BY total_mb DESC;

-- 查看未使用索引的查询
SELECT * FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE index_name IS NULL OR index_name = 'PRIMARY'
ORDER BY count_star DESC;
```

## 七、常见性能问题与对策

| 现象 | 可能原因 | 解决方案 |
|------|---------|---------|
| CPU 100% | 全表扫描、缺少索引 | EXPLAIN 分析，加索引 |
| IO 高 | 缓冲池太小 | 增大 `innodb_buffer_pool_size` |
| 锁等待 | 长事务、高并发 | 优化事务，减少锁持有时间 |
| 临时表 | GROUP BY/DISTINCT 无索引 | 加索引覆盖分组字段 |
| 数据量大 | 分页深、未归档 | 游标分页、定期归档 |

### 常见 SQL 优化案例

```sql
-- 1. 原 SQL（慢）
SELECT * FROM orders WHERE DATE(created_at) = '2025-01-15';

-- 优化：避免函数在索引列上
SELECT * FROM orders
WHERE created_at >= '2025-01-15 00:00:00'
  AND created_at < '2025-01-16 00:00:00';


-- 2. 原 SQL（慢）
SELECT * FROM users WHERE name LIKE '%张三%';

-- 优化：无法走索引，考虑全文索引
CREATE FULLTEXT INDEX idx_name ON users(name);
SELECT * FROM users WHERE MATCH(name) AGAINST('张三' IN BOOLEAN MODE);


-- 3. 原 SQL（慢）
SELECT * FROM users ORDER BY RAND() LIMIT 10;

-- 优化：避免 ORDER BY RAND()
SELECT * FROM users
WHERE id >= (SELECT FLOOR(MAX(id) * RAND()) FROM users)
ORDER BY id LIMIT 10;


-- 4. 原 SQL（慢）
UPDATE orders SET status = 1 WHERE status = 0;
-- 一次性更新大量数据

-- 优化：分批更新
UPDATE orders SET status = 1
WHERE status = 0 LIMIT 1000;
-- 在应用中循环执行
```

## 八、MySQL 配置优化

```ini
[mysqld]
# 缓冲池——最重要的配置，设置为内存的 60-70%
innodb_buffer_pool_size = 4G

# 日志缓冲
innodb_log_file_size = 512M
innodb_log_buffer_size = 64M

# IO 线程
innodb_read_io_threads = 8
innodb_write_io_threads = 8

# 脏页刷新
innodb_io_capacity = 2000
innodb_flush_neighbors = 0          # SSD 不需要刷邻居

# 连接
max_connections = 500
thread_cache_size = 100

# 临时表
tmp_table_size = 64M
max_heap_table_size = 64M

# 查询缓存（MySQL 8.0 已移除，不用配置）
# 排序和分组
sort_buffer_size = 2M
join_buffer_size = 2M
```

> 注意：`sort_buffer_size` 和 `join_buffer_size` 是会话级别的，不要设置过大（每个连接都会分配）。

## 九、优化流程总结

```
1. 打开慢查询日志 → 找到慢 SQL
2. EXPLAIN 分析执行计划 → 确认问题
3. 建立或优化索引 → 解决大部分问题
4. 优化 SQL 写法 → 解决剩余问题
5. 调整 MySQL 配置 → 硬件资源利用最大化
6. 数据层面优化 → 分区、分表、归档
7. 架构层面优化 → 读写分离、分布式
```

---

## 小结

性能优化以慢查询日志为入口，EXPLAIN 为分析工具，索引优化为核心手段。大部分性能问题都可以通过加合适的索引解决。
