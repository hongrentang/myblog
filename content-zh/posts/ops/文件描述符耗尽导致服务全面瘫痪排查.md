## 故障经过

**环境**：CentOS 7，16 vCPU，64GB 内存，单台裸金属服务器上以 systemd 形式运行着 12 个微服务。

**时间**：下午 2:30，一次常规部署刚刚完成——上线了 `order-service`（Java）的新版本。

**症状**：

部署后几分钟内，节点上的 12 个微服务**同时开始报错**：

```text
# order-service 日志
java.io.IOException: Too many open files
    at java.base/sun.nio.ch.SocketChannelImpl.checkConnect(Native Method)

# payment-service 日志
Caused by: java.net.SocketException: Too many open files

# notification-service 日志
java.io.FileNotFoundException: /var/log/notification/app.log (Too many open files)
```

连 SSH 登录都变得异常艰难：

```text
$ ssh production-node-01
-bash: fork: retry: Resource temporarily unavailable
ssh_exchange_identification: Connection closed by remote host
```

勉强登录上去之后，发现系统日志里满是失败记录：

```text
$ sudo tail -f /var/log/messages
Jun  9 14:32:15 production-node-01 systemd-logind: Failed to start user service 'user-1000.slice': Too many open files
Jun  9 14:32:15 production-node-01 systemd-logind: Failed to create session: Too many open files
```

节点**彻底瘫痪**——新进程无法启动，已有进程无法打开新文件或新连接。整个平台停摆了。

## 背景——Linux 文件描述符基础

在排查之前，先理解文件描述符是什么。

### 什么是文件描述符？

**文件描述符（File Descriptor, FD）** 是操作系统用来标识已打开文件、套接字、管道等 I/O 资源的非负整数。每次进程打开文件、建立网络连接或创建管道，内核就分配一个 FD。

### 进程级别限制：`ulimit -n`

每个进程都有 FD 打开数量限制，由 `ulimit -n`（nofile）控制：

- **软限制（Soft limit）**：有效限制，进程可自行提高到硬限制的值。
- **硬限制（Hard limit）**：绝对上限，只有 root 可以调高。

```bash
# 查看当前限制
ulimit -Sn   # 软限制
ulimit -Hn   # 硬限制
```

### 系统级别限制

内核还有全局限制：

- **`fs.file-max`**：系统范围内最多可打开的文件描述符数。
- **`fs.nr_open`**：每个进程硬限制的上限（通常为 1048576）。

```bash
# 查看系统 FD 统计
cat /proc/sys/fs/file-max        # 65535（多数系统默认值）
cat /proc/sys/fs/file-nr         # 6336  0   65535（已分配, 空闲, 最大值）
```

`file-nr` 输出三个数字：`已分配 | 空闲 | 最大值`——分别表示当前分配的 FD 数、已分配但未使用的空闲 FD 数、系统上限。

### FD 的消耗来源

| 资源 | 典型 FD 消耗 |
|------|-------------|
| 已打开的文件（日志、配置、数据） | 每个文件 1 个 FD |
| 网络套接字 | 每个连接 1 个 FD |
| 管道 | 每个管道 2 个 FD |
| epoll 实例 | 每个实例 1 个 FD |
| EventFd / TimerFd | 各 1 个 FD |

微服务环境中，**网络套接字**通常是最大 FD 消耗来源——每个 HTTP 请求、数据库连接、缓存连接和 RPC 调用都会消耗一个 FD。

## 排查过程

### 第一步：检查系统级 FD 使用量

先看系统范围内打开了多少文件描述符：

```bash
$ cat /proc/sys/fs/file-nr
65280  0  65535
```

**警铃大作**。系统已分配 65,280 个 FD，上限 65,535——使用率 **99.6%**，只剩 255 个 FD 可用。离全面枯竭只差一步。

### 第二步：找出谁在消耗 FD

```bash
$ for pid in /proc/[0-9]*; do
    echo "$(basename $pid) $(ls "$pid"/fd 2>/dev/null | wc -l)"
  done | sort -k2 -rn | head -10
```

输出：

```
28765 1024
31233 887
30122 654
28901 432
...
```

进程 28765 已经达到了每个进程的限制：**1024**——这正是 CentOS 7 上 `ulimit -n` 的默认值。

### 第三步：确认肇事进程

```bash
$ ps aux | grep 28765
java     28765  12.3  8.1  8.2g 5.4g ?  Ssl  14:25  4:32 /usr/bin/java -jar order-service.jar
```

是刚刚部署的 `order-service`。

```bash
$ cat /proc/28765/limits | grep "open files"
Max open files            1024                 4096                 files
```

软限制 1024，硬限制 4096。进程已经撞上了软限制的墙。

### 第四步：看看 FD 都是什么类型

```bash
$ ls -la /proc/28765/fd | head -20
total 0
dr-x------ 2 java java  ... .
dr-x------ 2 java java  ... ..
lrwxrwxrwx 1 java java  ... 0 -> /dev/null
lrwxrwxrwx 1 java java  ... 1 -> /dev/null
lrwxrwxrwx 1 java java  ... 10 -> socket:[1897201]
lrwxrwxrwx 1 java java  ... 11 -> socket:[1897202]
lrwxrwxrwx 1 java java  ... 12 -> socket:[1897203]
lrwxrwxrwx 1 java java  ... 13 -> socket:[1897204]
...
```

几乎全是**套接字**。用 `lsof` 确认：

```bash
$ lsof -p 28765 | head -30 | awk '{print $5}' | sort | uniq -c | sort -rn
   1024 IPv4
```

1024 个 FD 全部是 IPv4 套接字。连一个普通文件的 FD 都没有。

### 第五步：查看套接字状态

```bash
$ lsof -p 28765 | grep -c CLOSE_WAIT
8432
```

**8,432 个套接字处于 `CLOSE_WAIT` 状态**。这就是铁证。

> **CLOSE_WAIT** 表示对端已经关闭了连接，但本地应用程序（我们的 Java 代码）没有调用 `close()`。这些套接字处于半关闭状态，如果应用不清理，就会无限泄漏。

### 第六步：检查 systemd 服务配置

```bash
$ systemctl show order-service | grep -i limitnofile
LimitNOFILE=
LimitNOFILESoft=
```

两个都是空值——意味着该服务继承了 systemd 默认值，在 CentOS 7 上就是 **1024**。

### 第七步：检查系统级配置

```bash
$ sysctl fs.file-max
fs.file-max = 65535

$ ulimit -n
1024
```

用户进程默认 `ulimit -n` 为 1024。系统级 `fs.file-max` 是 65535，理论上可以容纳更多，但每个进程的限制先被击穿了——同时系统的总 FD 也即将耗尽。

---

## 根因分析

三个因素叠加在一起，造成了这次完美风暴。

### 1. 应用程序 Socket 泄漏（主因）

新部署的 `order-service`（Java）使用了一个 HTTP 连接池，但没有配置最大连接数限制。更糟糕的是，空闲连接没有被正确关闭：

```java
// 有 Bug 的代码——连接池在泄漏
public class OrderServiceClient {
    private CloseableHttpClient httpClient = HttpClients.createDefault();

    public Response callExternalApi(Request req) {
        // 默认 HttpClient 没有连接数限制
        // 空闲连接从未被回收
        // 没有连接超时或过期检测
        HttpGet httpGet = new HttpGet("https://external-api.example.com/orders");
        try {
            return httpClient.execute(httpGet, response -> {
                // 处理响应，但从未显式关闭连接
                return new Response(response.getEntity().getContent());
            });
        } catch (IOException e) {
            log.error("API call failed", e);
            // 异常路径也泄漏了连接
            throw new RuntimeException(e);
        }
    }
}
```

核心问题：
- `HttpClients.createDefault()` 创建的连接池默认**每路由最多 2 个连接、总数最多 20 个**，但上游 API 服务器设置了 keep-alive，导致连接被保持打开。
- 处理响应的代码路径打开了 `InputStream` 但从未调用 `close()`。
- 异常路径同样泄漏——发生异常时连接虽然返回到了连接池，但底层 socket 可能处于损坏状态。
- 没有配置空闲连接回收（`evictExpiredConnections()` / `evictIdleConnections()`）。
- 没有连接有效性检测（`setValidateAfterInactivity()`）。

随着时间的推移，HTTP 调用不断积累，连接池不断创建新连接却从不释放旧连接，造成了大规模 socket 泄漏。

### 2. 每个进程的 FD 限制过低（促成因素）

CentOS 7 默认 `ulimit -n` 是 **1024**。对于一个每秒处理数百个请求的 Java 微服务来说，这个数字远远不够。`order-service` 在启动后大约 **7 分钟**就撞上了这个限制。

```bash
# CentOS 7 的默认值——对现代服务来说太低
* soft nofile 1024
* hard nofile 4096
```

### 3. systemd 继承默认值（促成因素）

`order-service` 的 systemd unit 文件没有设置 `LimitNOFILE`，因此使用了 systemd 的默认值。

```ini
# order-service.service 中缺失了
[Service]
# LimitNOFILE=65536  <-- 没有设置
```

### 雪崩过程

1. `order-service` 从部署那一刻起就开始泄漏 socket。
2. 约 7 分钟后，达到单进程 1024 个 FD 的限制，无法再处理请求。
3. 服务停止响应健康检查，导致所有下游调用方降级。
4. 依赖 `order-service` 的其他服务开始堆积重试和排队请求，连接激增，各自迅速消耗 FD。
5. 节点级 FD 总数逼近 `fs.file-max`（65535）。
6. `systemd-logind` 无法为新 SSH 会话分配 FD → 登录失败。
7. 已有进程无法创建新线程（`fork()` 需要 FD）、无法写入日志、无法接受新连接。
8. **节点上的全部服务彻底瘫痪。**

---

## 解决方案

### 紧急恢复（5 分钟内）

停止泄漏，杀掉肇事进程：

```bash
# 定位并杀掉泄漏的服务
$ systemctl stop order-service
$ kill -9 28765   # 如果 FD 耗尽导致 systemctl 无法执行，用 kill -9
```

进程死亡的那一刻，内核回收了它的所有 FD。

```bash
$ cat /proc/sys/fs/file-nr
823  0  65535
```

FD 使用量从 65,280 降到了 823。**所有其他服务立刻恢复**——它们可以打开文件、接受连接、写入日志了。SSH 登录也恢复正常。

### 短期加固（30 分钟内）

在下一个版本部署之前，提高各项限制防止复发：

**通过 systemd 设置每个进程的限制：**

```bash
$ systemctl edit order-service
```

添加：

```ini
[Service]
LimitNOFILE=65536
LimitNOFILESoft=65536
```

然后：

```bash
$ systemctl daemon-reload
$ systemctl restart order-service
```

验证：

```bash
$ cat /proc/$(pidof order-service)/limits | grep "open files"
Max open files            65536                65536                files
```

**系统级限制：**

```bash
# 提高内核上限
$ echo "fs.file-max = 200000" >> /etc/sysctl.conf
$ sysctl -p

# 提高用户级别限制
$ echo "* soft nofile 65536" >> /etc/security/limits.conf
$ echo "* hard nofile 65536" >> /etc/security/limits.conf
```

### 根本修复（代码变更）

核心问题是 Java HTTP 连接池泄漏。修复代码：

```java
// 修复后的代码——正确的连接池管理
public class OrderServiceClient {
    private final CloseableHttpClient httpClient;

    public OrderServiceClient() {
        // 使用连接池管理器，设置合理上限
        PoolingHttpClientConnectionManager poolManager =
            new PoolingHttpClientConnectionManager();
        poolManager.setMaxTotal(200);
        poolManager.setDefaultMaxPerRoute(50);
        // 连接闲置 5 秒后进行有效性检测
        poolManager.setValidateAfterInactivity(5000);

        this.httpClient = HttpClients.custom()
            .setConnectionManager(poolManager)
            .setConnectionTimeToLive(30, TimeUnit.SECONDS)
            .evictExpiredConnections()
            .evictIdleConnections(30, TimeUnit.SECONDS)
            .build();
    }

    public Response callExternalApi(Request req) {
        HttpGet httpGet = new HttpGet("https://external-api.example.com/orders");
        try (CloseableHttpResponse response = httpClient.execute(httpGet)) {
            // try-with-resources 确保 response 一定会被关闭
            return new Response(EntityUtils.toByteArray(response.getEntity()));
        } catch (IOException e) {
            log.error("API call failed", e);
            throw new RuntimeException(e);
        }
    }
}
```

关键修复点：
- `PoolingHttpClientConnectionManager` 显式设置最大连接数。
- `evictExpiredConnections()` 和 `evictIdleConnections(30, TimeUnit.SECONDS)`——后台线程定时回收空闲连接。
- `setValidateAfterInactivity(5000)`——使用前验证连接是否有效。
- `try-with-resources`——确保无论是否发生异常，`close()` 都会被调用。
- `EntityUtils.toByteArray()`——正确消费并关闭实体流。

## 经验教训

### 1. 永远不要相信默认值

CentOS 7 默认 `ulimit -n` 的 **1024** 是为一个服务器只跑几个简单服务的时代设计的。现代 Java 微服务在负载下几秒钟就能耗尽这个数值。**务必在 systemd unit 文件中显式设置资源限制。**

### 2. 连接池必须有上限

每个 HTTP 客户端、数据库连接池和网络库都必须配置：
- **最大上限**（不要盲目使用默认值）
- **空闲超时**（回收过期连接）
- **有效性检测**（不要重用死连接）
- **正确关闭**（try-with-resources 或 finally 块）

### 3. 监控、监控、再监控

FD 耗尽在酿成灾难之前是悄无声息的。和 CPU、内存不同，你不会感受到渐进式降级——只会撞上一堵硬墙。在你的监控系统中追踪 `file-nr` 和每个进程的 FD 数量。

### 4. 雪崩效应是真实存在的

一个服务的资源泄漏可以拖垮整个节点。当 `systemd-logind` 无法分配 FD 时，你就无法 SSH 登录去修复。当一个进程无法 `fork()` 时，你连 `kill` 命令都跑不了。这就造成了**拒绝服务死锁**，必须通过带外访问（IPMI、iDRAC 或物理重启）才能解决。

### 5. systemd vs /etc/security/limits.conf 的区别

重要区别：
- **`/etc/security/limits.conf`** 适用于基于 PAM 的登录方式（SSH、控制台），**不适用于** systemd 服务。
- **systemd 服务**必须在 unit 文件中使用 `LimitNOFILE=` 进行配置。
- **两者都需要设置**才能做到全面覆盖。
