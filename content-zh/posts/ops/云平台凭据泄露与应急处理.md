# 云平台凭据泄露事件——AWS 密钥写入公开仓库，一夜烧掉五万美元

## 常见搜索词

- aws access key 暴露在公开 github 仓库
- 云平台凭据泄露应急响应
- aws 密钥被自动扫描器窃取
- kubernetes service account token 泄露
- 密钥扫描 pre-commit hook 预防

---

## 故障经过

**环境**: 基于 AWS (EKS) 的 Kubernetes 集群，3 个生产集群分布在 us-east-1 和 eu-west-1，150+ 微服务，基础设施通过 Terraform 管理，代码存储在**公开**的 GitHub 单仓库中。

**时间**: 周二 14:30 UTC。基础设施团队的一名工程师提交了一个包含基础设施配置的 commit。12 分钟内，AWS Cost Explorer 显示垂直暴涨。到 14:50 UTC——仅 20 分钟后——公司的监控 Slack 频道被"AWS 预算告警：已超过 $5,000"刷屏。

**初始症状**:

```bash
# AWS 预算告警——异常的第一个信号
预算名称: monthly-soft-limit
阈值: 80% ($4,000 / $5,000)
当前消费: $5,320
预测: $38,000
```

值班工程师打开 AWS CloudTrail，看到 API 调用来自俄罗斯、中国和尼日利亚的 IP——这些区域公司完全没有业务。

```bash
# CloudTrail 控制台——异常 API 活动
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=ResourceType,AttributeValue=AWS::EC2::Instance \
  --start-time "2026-06-03T14:30:00Z" \
  --query 'Events[?contains(SourceIPAddress, `185.`) || contains(SourceIPAddress, `102.`)]' \
  --max-items 50
```

**影响**: 18 小时内产生 $50,300 的非授权 AWS 费用。3 个包含客户 PII 的 S3 存储桶被访问。6 个 AWS 区域启动了 1,200+ 台 GPU 竞价实例。全账户凭据轮换。生产部署冻结 36 小时。需向 2 名客户发送数据泄露通知。

---

## 背景

六个月前，基础设施团队为 Kubernetes 服务集成了跨账户 IAM 角色。为某个需要读取 S3 存储桶指标的监控工具生成了一个 AWS Access Key（`AKIAIOSFODNN7EXAMPLE`），权限为 `ReadOnlyAccess` + `S3:GetObject`。

这个密钥原本只是用于快速概念验证，从未打算投入生产。但因为它能用，就留下来了。一名开发者为了方便，把它加到了 Kubernetes ConfigMap 中：

```yaml
# configmap-infra.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: monitoring-config
data:
  aws_access_key_id: AKIAIOSFODNN7EXAMPLE
  aws_secret_access_key: wJalrXUtpnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
  s3_bucket: production-customer-backups
```

这个 ConfigMap 被检入了基础设施单仓库。该仓库从一开始就是**公开**的——团队的理念是"开源我们的基础设施模式"。

一个由凭证窃取团伙运营的自动扫描器正在扫描公开 GitHub 仓库的提交历史。正则表达式 `AKIA[0-9A-Z]{16}` 立即匹配成功。攻击者在 commit 提交后 3 分钟内就获得了可用的密钥对。

## 排查过程

### 第一步：确认凭据暴露

```bash
# 检查 GitHub 仓库的公开访问权限
# 仓库是公开的——任何人都可以克隆

# 搜索提交历史中的凭据模式
git log --all --oneline | head -5
git show HEAD --stat | grep -i "configmap"

# 使用 GitHub 的密钥扫描 API 确认暴露
gh api repos/org/infra-config/secret-scanning/alerts \
  --jq '.[] | select(.secret_type == "aws_access_key")'
```

一条告警确认：GitHub 的密钥扫描器检测到了 AWS Access Key。但告警发送到了一个无人监控的邮件别名。

**总计：1,200 台实例**——全部为 GPU 优化型，专用于加密货币挖矿。


3 个 S3 存储桶被访问——其中一个包含未加密的客户 PII（姓名、电子邮件地址、电话号码）。

### 第三步：追溯攻击者行为

CloudTrail 日志和 EC2 控制台活动揭示了攻击者的时间线：

| 时间 (UTC) | 操作 | 详情 |
|-----------|------|------|
| 14:33 | 凭据发现 | 扫描 GitHub 仓库，正则匹配 AKIA 密钥 |
| 14:34 | 凭据验证 | 从 IP 185.xx.xx.xx 调用 `sts:GetCallerIdentity` |
| 14:35 - 14:50 | 资源枚举 | `ec2:DescribeInstances`, `s3:ListBuckets`, `iam:GetUser` |
| 14:35 - 15:10 | 部署挖矿程序 | 6 个区域启动 1,200 台 GPU 竞价实例 |
| 14:40 | 持久化 | 创建 IAM 用户 `support-engineer-02` 并授予 `AdministratorAccess` |
| 14:42 - 14:48 | 数据窃取 | 从 S3 存储桶下载 12 GB 数据（客户备份） |
| 14:55 | 横向移动 | 尝试 `eks:DescribeCluster`——被网络策略阻止 |

### 第四步：定位泄露源头

```bash
# 找到引入凭据的 commit
git log --all --oneline --source -S "AKIAIOSFODN"
```

凭据在 commit `a3f2b1c` 中被引入到 `main` 分支，合并时间比第一条 CloudTrail 异常早 12 分钟。文件 `configmap-infra.yaml` 中包含明文的 AWS Access Key 和 Secret Key。

---

## 根因

1. **ConfigMap 中的明文云平台凭据**：AWS Access Key 和 Secret Key 被直接硬编码在 Kubernetes ConfigMap YAML 文件中。没有使用任何密钥管理工具（AWS Secrets Manager、HashiCorp Vault 或 Sealed Secrets）

2. **包含敏感基础设施代码的公开仓库**：基础设施单仓库是公开的。提交到 `main` 分支的任何文件都会立即被自动扫描器发现。没有分支保护规则阻止直接推送到 `main`

3. **没有 pre-commit 密钥检测钩子**：没有配置 `pre-commit` 钩子、`talisman` 或 `gitleaks` 来阻止包含凭据模式的提交

4. **IAM 策略权限过大**：虽然密钥标记为"只读"，但 IAM 策略允许对所有 S3 存储桶（`arn:aws:s3:::*`）执行 `s3:GetObject` 操作，未限定到特定存储桶。这使攻击者能够从客户数据存储桶窃取数据

5. **IAM Access Key 无使用限制**：密钥没有 `aws:SourceIp` 或 `aws:SourceArn` 条件限制——没有限制可以从哪里使用。攻击者从自己的基础设施中使用它

6. **没有资源级预算告警**：AWS 预算告警设置在账户级别，但阈值太高（$5,000）。第一条告警到达时已经产生了 $5,000 的消费。没有按服务或按区域的预算限制

---

## 解决方案

### 应急处置（前 30 分钟）

```bash
# 第一步：停用被泄露的 Access Key
aws iam update-access-key \
  --access-key-id AKIAIOSFODNN7EXAMPLE \
  --status Inactive

# 第二步：删除攻击者创建的 IAM 用户
aws iam delete-user --user-name support-engineer-02
# （需要先分离策略并删除 Access Key）

# 第三步：分离并删除未授权的策略
aws iam list-attached-user-policies --user-name support-engineer-02
aws iam detach-user-policy --user-name support-engineer-02 \
  --policy-arn arn:aws:iam::aws:policy/AdministratorAccess

# 第四步：终止所有非授权 EC2 实例
aws ec2 describe-instances \
  --filters "Name=instance-state-name,Value=running" \
  --query 'Reservations[].Instances[?LaunchTime>`2026-06-03T14:30:00Z`].[InstanceId,Placement.Region]' \
  --output text | awk '{print $2, $1}' | while read region id; do
    aws ec2 terminate-instances --instance-ids "$id" --region "$region"
  done

# 第五步：删除未授权的安全组规则
aws ec2 describe-security-groups \
  --query 'SecurityGroups[?GroupName!=`default`].[GroupId,GroupName]' \
  --output text | xargs -r -I{} aws ec2 delete-security-group --group-id {}
```

### 遏制验证

```bash
# 验证密钥不再活跃
aws iam get-access-key-last-used \
  --access-key-id AKIAIOSFODNN7EXAMPLE

# 检查剩余未授权资源
aws resourcegroupstaggingapi get-resources \
  --query 'ResourceTagMappingList[].ResourceARN'

# 轮换账户中所有剩余的 IAM 密钥
aws iam list-users --query 'Users[].UserName' --output text | \
  while read user; do
    aws iam list-access-keys --user-name "$user" --query 'AccessKeyMetadata[].AccessKeyId' --output text | \
    while read key; do
      aws iam create-access-key --user-name "$user"
      aws iam update-access-key --access-key-id "$key" --status Inactive
    done
  done
```

### 长期修复

**1. 实施密钥管理**

```yaml
# 使用 AWS Secrets Manager + External Secrets Operator
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: aws-credentials
spec:
  secretStoreRef:
    name: aws-secretsmanager
    kind: SecretStore
  target:
    name: aws-credentials
  data:
    - secretKey: aws_access_key_id
      remoteRef:
        key: /infra/aws/monitoring-key
        property: access_key_id
    - secretKey: aws_secret_access_key
      remoteRef:
        key: /infra/aws/monitoring-key
        property: secret_access_key
```

**2. 实施 IAM 最小权限**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::monitoring-metrics/*",
      "Condition": {
        "IpAddress": {
          "aws:SourceIp": "10.0.0.0/8"
        }
      }
    }
  ]
}
```

**3. 添加 Pre-Commit 钩子**

```bash
# .gitleaks.toml — 阻止包含凭据的提交
[[rules]]
id = "aws-access-key"
description = "AWS Access Key"
regex = '''AKIA[0-9A-Z]{16}'''
tags = ["aws", "credentials"]

[[rules]]
id = "aws-secret-key"
description = "AWS Secret Key"
regex = '''(?i)aws(.{0,20})?['\"][0-9a-zA-Z\/+]{40}['\"]'''
tags = ["aws", "credentials"]
```

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.5.0
    hooks:
      - id: detect-private-key
```

**4. CI/CD 密钥扫描**

```yaml
# GitHub Actions — 每次推送都扫描
name: Secret Scanning
on: [push, pull_request]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

**5. IAM 条件和服务控制策略 (SCP)**

```json
// 服务控制策略——对所有 IAM 用户强制执行约束
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RestrictEC2InstanceTypes",
      "Effect": "Deny",
      "Action": "ec2:RunInstances",
      "Resource": "arn:aws:ec2:*:*:instance/*",
      "Condition": {
        "StringNotEquals": {
          "ec2:InstanceType": ["t3.medium", "t3.large", "m5.large", "c5.large"]
        }
      }
    },
    {
      "Sid": "RequireIAMConditions",
      "Effect": "Deny",
      "Action": "iam:CreateAccessKey",
      "Resource": "*",
      "Condition": {
        "Null": {
          "aws:RequestedRegion": "true"
        }
      }
    }
  ]
}
```

## 经验教训

- **Kubernetes 清单中的明文凭据就是炸弹**：ConfigMap 和 Secret 中**绝不能**包含原始的云平台凭据。使用 External Secrets Operator、Sealed Secrets 或 Vault。如果在 YAML 文件中看到 `aws_access_key_id: AKIA...`，立即假设它已经泄露

- **公开仓库 + 基础设施代码 = 生存风险**：团队"开源基础设施模式"的理念直接导致了这次入侵。安全不是靠隐藏，但让你的 IAM 配置可以被公开搜索是极其危险的

- **IAM 条件能拯救账户**：在 IAM 策略中添加 `aws:SourceIp` 和 `aws:SourceArn` 条件，即使密钥泄露，也能阻止攻击者在 VPC 外部使用它

- **预算告警需要多层级、激进设置**：单个 $5,000 的账户级预算告警远远不够。设置按区域、按服务、按账户的预算告警，阈值分别为 50/75/90/100%。CloudWatch 对账单指标的异常检测能够在近实时捕获异常

- **GitHub 密钥扫描告警需要主动监控**：GitHub 内置的密钥扫描器发现了密钥，但将告警发送到了无人监控的邮箱。将其集成到 PagerDuty 或 Slack。将密钥扫描告警作为 P0 事件处理

- **Pre-commit 钩子是强制性的**：一个简单的 `gitleaks` pre-commit 钩子就能阻止包含 AWS 密钥的提交。没有理由不设置这个。只需 5 分钟配置，就能预防此类事件

- **不可变基础设施标签非常有价值**：为所有授权的 EC2 实例打上 `Environment: Production` 和 `ManagedBy: Terraform` 标签，使得编写脚本终止 1,200 台未授权实例变得非常容易

## 总结

攻击链路：

```
开发者将 AWS 凭据硬编码在 ConfigMap YAML 中
→ 将 configmap-infra.yaml 提交到公开仓库的 main 分支
→ GitHub 密钥扫描器检测到密钥，发送邮件到无人监控的别名
→ 攻击者的自动爬虫扫描公开 GitHub 提交中的 AKIA 模式
→ 爬虫通过 sts:GetCallerIdentity 验证凭据（提交后 3 分钟）
→ 枚举资源：EC2、S3、IAM（提交后 5 分钟）
→ 在 6 个区域启动 1,200 台 GPU 竞价实例用于挖矿（提交后 5-40 分钟）
→ 创建具有 AdministratorAccess 的 IAM 持久化用户
→ 从 S3 窃取 12 GB 客户 PII 数据（提交后 10 分钟）
→ AWS 预算告警在 $5,000 时触发——提交后 18 分钟
→ 值班工程师停用密钥、终止实例
→ $50,300 账单、3 次数据泄露通知、36 小时部署冻结
```

**修复用时**：36 小时。**损失**：$50,300 + 3 次数据泄露通知带来的法律/合规后果。**根因**：一个包含硬编码凭据的 ConfigMap 被提交到了公开仓库。

修复链路：

```
ConfigMap 中的硬编码密钥
→ 替换为 External Secrets Operator + AWS Secrets Manager
→ 添加 gitleaks pre-commit 钩子（阻止 AKIA 模式）
→ 每次推送添加 gitleaks CI 任务
→ 将 IAM 策略限定到特定资源 ARN + SourceIp 条件
→ 应用 SCP 限制实例类型并强制执行 IAM 条件
→ 设置按区域预算告警（50/75/90/100%）并通过 SNS 发送到 PagerDuty
→ 将基础设施仓库设为私有
→ 将 GitHub 密钥扫描告警集成到事件管理平台
```

一个硬编码的凭据。十二分钟被发现的窗口。十八小时的挖矿。三次客户数据泄露。五万美元。所有这一切，本可以用一个 pre-commit 钩子和一条 IAM 条件来预防。
