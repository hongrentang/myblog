# 容器镜像漏洞引入生产隐患——两年未更新的基础镜像导致远程代码执行

## 常见搜索词

- 容器镜像漏洞利用
- 旧基础镜像 rce 漏洞
- trivy 扫描容器镜像 ci/cd
- kubernetes 镜像漏洞管理
- docker 基础镜像安全扫描

---

## 故障经过

**环境**: K8S v1.28, 生产集群, 50+ 微服务。镜像通过 GitHub Actions 构建，推送至 Docker Hub。

**时间**: 周一 07:30。WAF 告警：对内容管理服务的 `/api/upload` 的异常 POST 请求，载荷匹配已知 RCE 利用模式。

**初始症状**: 内容管理应用开始返回 500 错误。Pod 日志显示进程崩溃和意外文件写入。

```bash
[2026-06-03 07:28:15] POST /api/upload 200
[2026-06-03 07:28:16] WARNING: child process exited with signal SIGSEGV
[2026-06-03 07:28:17] File created: /tmp/.systemd-update.sh
[2026-06-03 07:28:18] Connecting to 45.xxx.xxx.xxx:4443...
```

**影响**: 一个容器被攻破。挖矿程序被植入。3 个 S3 存储桶的数据可能被窃取。服务下线 2 小时进行取证分析。

---

## 背景

内容管理服务是 18 个月前构建的，一直正常运行至今。Dockerfile 很简单：

```dockerfile
FROM node:14-alpine          # ← 2021 年 3 月发布——2 年多没更新
WORKDIR /app
COPY package.json .
RUN npm install
COPY src/ .
EXPOSE 3000
CMD ["node", "app.js"]
```

基础镜像 `node:14-alpine` 固定了大版本但拉取的是最新的次要版本——仍然有 2 年历史。随着时间的推移，Node.js 运行时和 Alpine 基础层中发现了漏洞。

漏洞扫描会发现这些 CVE：

| CVE | 严重度 | 组件 | 描述 |
|-----|--------|------|------|
| CVE-2024-xxx1 | 严重 | Node.js 14 | 通过 HTTP/2 的远程代码执行 |
| CVE-2024-xxx2 | 高 | Node.js 14 | `undici` 原型污染 |
| CVE-2024-xxx3 | 严重 | libuv | DNS 解析器缓冲区溢出 |
| CVE-2024-xxx4 | 高 | OpenSSL | TLS 证书验证绕过 |

攻击者通过互联网扫描发现该服务，从响应头识别为 Node.js，利用 CVE-2024-xxx1（已知 Node.js HTTP/2 RCE）入侵了服务。

当时的 CI/CD 流水线没有镜像扫描。

---

## 排查过程

### 第一步：识别漏洞

```bash
trivy image cms:latest | head -30
```

```
node:14-alpine (alpine 3.14.2)
=========================================
总计: 127 个漏洞 (17 个严重, 42 个高, 68 个中)

CVE-2024-xxx1 (严重): Node.js HTTP/2 中的 RCE → 在 Node 14.21.3+ 中修复
CVE-2024-xxx3 (严重): libuv 中的缓冲区溢出 → 在 libuv 1.44.2+ 中修复
```

### 第二步：确认被利用

攻击者通过 RCE 漏洞上传了挖矿程序。该 Pod 运行在 2 年未更新的基础镜像上。

### 第三步：检查数据外传

被攻陷的容器已建立到攻击者 IP 的出站连接。S3 访问日志显示来自该 Pod IP 的请求访问了该服务通常不访问的存储桶。

### 第四步：评估爆炸半径

检查所有运行中的镜像后，50 个服务中有 12 个的基础镜像存在严重漏洞。4 个已运行超过一年未重建。

---

## 根因

1. **CI/CD 中无镜像扫描**：安全漏洞扫描不是构建流水线的一部分。具有已知 CVE 的镜像被构建和部署而没有任何警告
2. **基础镜像过时**：`node:14-alpine` 有 2 年历史，累积了大量严重漏洞。没有定期更新基础镜像的流程
3. **无自动镜像重建**：即使上游基础镜像被修补，运行中的镜像也从未被重建。"如果它能跑，就别碰它"
4. **无漏洞 SLA**：没有要求在定义的时间范围内修复严重 CVE
5. **无运行时扫描**：没有在运行时监控已知漏洞镜像

---

## 解决方案

### 紧急处置

```bash
# 1. 删除被攻破的 Pod
kubectl delete pod cms-pod-7d9f8c6b-x

# 2. 使用重建的镜像更新部署
docker build -t cms:patched --build-arg BASE_IMAGE=node:20-alpine .
kubectl set image deployment/cms cms=cms:patched

# 3. 阻断到攻击者 IP 的出站流量
```

### 修复基础镜像

```dockerfile
FROM node:20-alpine    # 使用当前 LTS 版本
```

### CI/CD 添加镜像扫描

```yaml
- name: Scan for vulnerabilities
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: cms:${{ github.sha }}
    exit-code: 1
    severity: CRITICAL,HIGH
```

### 自动化基础镜像更新

使用 Dependabot 或 Renovate 每周自动检查 Docker 基础镜像更新。

### 漏洞修复 SLA

| 严重度 | 修复时间 | 要求 |
|--------|---------|------|
| 严重 | 24 小时 | 立即修补或阻断部署 |
| 高 | 7 天 | 在下个迭代中安排修补 |
| 中 | 30 天 | 在待办列表中跟踪 |

---

## 经验教训

- **基础镜像是供应链依赖**：像对待任何其他依赖一样对待 `FROM node:14-alpine`。固定版本、定期扫描、及时更新
- **"它能跑"不等于"它是安全的"**：两年的镜像正常运行直到出事那天。届时 CVE 已公开数月，利用代码随手可得
- **CI/CD 中的镜像扫描防止错误部署**：一个 `trivy scan --exit-code 1` 步骤就能阻断这次部署或至少标记风险
- **每周基础镜像更新应该是标配**：Dependabot/Renovate 自动化让 Docker 基础镜像保持最新。这不是额外工作——这是预防
- **严重 CVE 在 48 小时内就有公开利用代码**：如果你运行中的镜像有超过 48 小时的严重 CVE，假设利用代码已经存在

---

## 总结

攻击链路：

```
应用基于 node:14-alpine 构建（2 年未更新）
→ 镜像构建并部署时没有漏洞扫描
→ 基础镜像中有 127 个已知漏洞，17 个严重
→ CVE-2024-xxx1 (Node.js HTTP/2 RCE) 发布——利用代码可用
→ 攻击者扫描互联网，发现 Node.js 服务，部署利用
→ 挖矿程序被上传，数据被窃取
→ 服务下线 2 小时进行取证分析
```

恢复：2 小时。修复：1 小时（基础镜像更新 + 扫描集成）。根因：第一条 CI/CD 流水线中本应存在的漏洞扫描，时间为 0 分钟。尽早扫描，经常扫描。或者在入侵之后扫描——你自己选。
