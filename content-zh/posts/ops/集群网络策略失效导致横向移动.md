# 集群网络策略失效导致横向移动——一个前端漏洞引发的全集群数据泄露

## 常见搜索词

- kubernetes networkpolicy 横向移动
- k8s pod 间网络隔离
- default deny networkpolicy kubernetes
- 零信任网络 kubernetes
- 如何防止 k8s 横向移动

---

## 故障经过

**环境**: K8S v1.28, Calico CNI, 15 个命名空间中运行 200+ 微服务，集群已运行 3 年。

**时间**: 凌晨 02:10。IDS 告警：检测到来自异常源的生产 PostgreSQL 数据库流量。

**初始症状**: 生产 PostgreSQL 数据库收到来自前端 Node.js Pod 的查询——这在以前从未发生过。数据库只应被后端 API 服务访问。

```bash
# IDS 检测到的可疑连接
来源: frontend/web-app-7d9f8c6b-x (10.244.3.15)
目标: database/postgres-primary-0 (10.244.1.5)
端口: 5432 (PostgreSQL)
协议: TCP
查询: SELECT * FROM users; DROP TABLE payments;  # ← 恶意操作
```

**影响**: 生产数据库被入侵。客户支付记录被部分删除。从备份恢复数据耗时 6 小时。

---

## 背景

这个集群三年前首次部署时，团队急于上线。Kubernetes NetworkPolicy 一直在路线图上——但总被延后。"下个迭代再搞。"

结果：整个集群零个 NetworkPolicy。每个 Pod 都可以访问其他任何 Pod：

```bash
# 没有 NetworkPolicy 时，从任何 Pod 都可以：
kubectl exec -it frontend/web-app-abc -- bash
curl database-svc.production.svc.cluster.local:5432  # ← 没有策略阻止
curl redis-svc.cache.svc.cluster.local:6379            # ← 没有策略阻止
```

一个通过 Web 框架 RCE 漏洞被攻陷的前端 Pod 能够访问集群中的任何服务。

攻击者利用了 CVE-2026-12345（Node.js Express 框架的已知 RCE 漏洞）。进入后，他们扫描了内部网络：

```bash
# 从被攻陷的前端容器内部
for svc in api-gateway database redis payment auth; do
  for ns in production staging cache; do
    host="${svc}.${ns}.svc.cluster.local"
    if timeout 1 bash -c "echo >/dev/tcp/$host/80" 2>/dev/null; then
      echo "开放: $host:80"
    fi
  done
done
```

他们发现从前端可以访问 40+ 个内部服务。扁平化网络给了他们无限通行证。

---

## 排查过程

### 第一步：确定入口点

```bash
# 检查哪个 Pod 发起了恶意数据库查询
grep "10.244.3.15" /var/log/kubernetes/audit.log | grep "5432" | head -5
```

追溯到 `frontend/web-app-7d9f8c6b-x`。该 Pod 因未修补的库存在 RCE 漏洞被利用。

### 第二步：绘制爆炸半径

```bash
# 从应急响应 Pod 检查该节点上哪些内部服务可达
kubectl get pods -n production -o wide | grep 10.244.3
```

攻击者已连接到：
- `database`（PostgreSQL）— 提取并删除了支付记录
- `redis`（缓存）— 转储了会话 Token
- `payment-api`（支付处理）— 尝试发起退款交易
- `auth`（认证）— 尝试提取凭据

### 第三步：确认不存在 NetworkPolicy

```bash
kubectl get networkpolicy --all-namespaces
# No resources found — 整个集群零个网络策略
```

```bash
# 确认：任何 Pod 都能访问任何服务
kubectl run test-pod --image=busybox -it --rm -- wget -qO- http://database-svc.production:5432
# 连接成功——完全开放
```

---

## 根因

1. **未定义任何 NetworkPolicy**：集群运行 3 年，没有一条 NetworkPolicy 资源
2. **Kubernetes 默认扁平网络**：默认允许所有 Pod 间通信。没有显式策略时，每个 Pod 都能访问其他 Pod
3. **没有纵深防御**：即使 RCE 漏洞最终被修补，NetworkPolicy 也能将爆炸半径限制在前端层
4. **没有东西向流量监控**：IDS 只监控南北向流量。内部横向移动完全不可见，直到数据库已被入侵

---

## 解决方案

### 紧急处置（遏制）

```bash
# 立即隔离被入侵的命名空间
kubectl label namespace production pod-security.kubernetes.io/enforce=restricted

# 删除并重新部署修复后的前端应用
kubectl delete deployment web-app -n frontend
kubectl apply -f frontend-deployment-patched.yaml

# 强制轮换所有数据库凭据
kubectl exec -it postgres-primary-0 -n production -- psql -c "ALTER USER app_user WITH PASSWORD 'new-password';"

# 失效所有 Redis 会话
kubectl exec -it redis-master-0 -n cache -- redis-cli FLUSHALL

# 从备份恢复数据库
kubectl exec -it postgres-primary-0 -n production -- psql -f /backups/2026-05-28-full.sql
```

### 部署默认拒绝网络策略

```yaml
# 默认拒绝所有入站流量（应用到所有命名空间）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes:
  - Ingress
---
# 默认拒绝所有出站流量
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
spec:
  podSelector: {}
  policyTypes:
  - Egress
```

### 实施基于层的微分段

```yaml
# 前端层：只接受互联网流量，只访问 API 层
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: frontend-network
  namespace: frontend
spec:
  podSelector:
    matchLabels:
      tier: frontend
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - ipBlock:
        cidr: 0.0.0.0/0
      ports:
      - port: 443
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          tier: api
    ports:
    - port: 8080
    - port: 8443
---
# API 层：只接受前端流量，访问数据库和缓存
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-network
  namespace: api
spec:
  podSelector:
    matchLabels:
      tier: api
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          tier: frontend
    ports:
    - port: 8080
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          tier: database
    ports:
    - port: 5432
  - to:
    - namespaceSelector:
        matchLabels:
          tier: cache
    ports:
    - port: 6379
---
# 数据库层：只接受 API 层流量
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: database-network
  namespace: database
spec:
  podSelector:
    matchLabels:
      tier: database
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          tier: api
    ports:
    - port: 5432
```

### 命名空间打标用于策略选择器

```bash
kubectl label namespace frontend tier=frontend
kubectl label namespace api tier=api
kubectl label namespace database tier=database
kubectl label namespace cache tier=cache
```

### 验证

```bash
# 验证：前端不能直接访问数据库
kubectl run test-pod --image=busybox -n frontend -it --rm -- wget -qO- http://database-svc.database:5432
# 连接超时——策略生效

# 验证：API 层可以访问数据库
kubectl run test-pod --image=busybox -n api -it --rm -- wget -qO- http://database-svc.database:5432
# 连接成功——权限正确
```

### 长期预防

1. **NetworkPolicy 纳入 CI/CD**：拒绝不包含 NetworkPolicy 清单的部署
2. **定期网络审计**：使用 `kubectl netpol` 或 `kubeaudit` 扫描没有策略的命名空间
3. **零信任网络**：通过准入控制器为新命名空间默认拒绝所有流量
4. **东西向流量监控**：部署服务网格（Istio/Linkerd）或基于 eBPF 的监控（Cilium）用于内部流量可见性
5. **漏洞扫描**：更快修补已知 CVE——这里使用的 RCE 漏洞已有修复补丁 3 周

---

## 经验教训

- **Kubernetes 扁平网络默认不安全**："Pod 可以访问一切"是默认配置。安全需要显式的 NetworkPolicy 配置
- **NetworkPolicy 是你的爆炸半径遏制工具**：即使存在应用漏洞，NetworkPolicy 也能阻止攻击者触及其它层
- **先默认拒绝，再显式放行**：从 `default-deny-ingress` 和 `default-deny-egress` 开始，然后添加精细的放行规则
- **纵深防御**：不要依赖单一安全控制。NetworkPolicy + 运行时安全 + 漏洞扫描 + 监控协同工作
- **为命名空间打标便于策略选择**：使用一致的基于层的打标方案（`tier: frontend`、`tier: api`、`tier: database`）来编写清晰可维护的策略

## 总结

攻击链路：

```
前端 Pod 存在未修补的 RCE 漏洞（CVE-2026-12345）
→ 攻击者获取前端容器的 Shell 权限
→ 扫描内部网络：发现 40+ 个可达服务
→ 直接连接 PostgreSQL（没有任何 NetworkPolicy 阻止）
→ 提取并删除支付记录
→ 转储 Redis 会话 Token
→ 尝试通过支付 API 发起欺诈交易
```

遏制：30 分钟。数据恢复：6 小时。修复（NetworkPolicy）：2 天部署。RCE 是火花——但扁平网络是燃料。NetworkPolicy 隔离一切。先默认拒绝。
