# 特权容器逃逸事件排查实录——一个调试 Pod 如何变成集群级别的 Root 后门

## 常见搜索词

- 特权容器逃逸 kubernetes
- 容器突破到宿主机
- kubectl debug 特权安全风险
- 如何防止容器逃逸
- 容器运行时安全事件

---

## 故障经过

**环境**: K8S v1.28, containerd 1.7, 3 Master + 5 Worker, 200+ 微服务。

**时间**: 凌晨 03:15。CrowdStrike 安全告警触发——`node-04` 上检测到异常进程执行。

**初始症状**: 已知的门罗币挖矿程序在一个 Worker 节点上运行。进程树显示它是在一个容器内启动的——但这个容器本不应有挖矿能力。

```bash
# 从应急响应节点执行
kubectl get pods --all-namespaces | grep -i node-04
NAMESPACE   NAME                     READY   STATUS    NODE
production  api-gateway-7d9f8c6b-x  1/1     Running   node-04
staging     debug-pod-nginx          1/1     Running   node-04    # ← 这是什么?
```

**影响**: 宿主机沦陷，集群凭证被窃取。全集群应急响应、取证分析、凭证轮换耗时 4 小时。

---

## 背景

两周前，一名开发人员在排查 staging 环境的网络问题。他需要检查容器内的网络流量。最快的办法：部署一个带 `privileged: true` 和宿主机网络访问权限的调试 Pod。

```yaml
# 这一切的起点——调试 Pod
apiVersion: v1
kind: Pod
metadata:
  name: debug-pod-nginx
  namespace: staging
spec:
  containers:
  - name: debug
    image: nginx:latest
    securityContext:
      privileged: true    # ← 完全宿主机访问权限
      capabilities:
        add: ["SYS_ADMIN", "NET_ADMIN", "SYS_PTRACE"]
    volumeMounts:
    - name: host-root
      mountPath: /host
  volumes:
  - name: host-root
    hostPath:
      path: /             # ← 挂载宿主机根文件系统
  restartPolicy: Never
```

这个 Pod 本应是临时的——定位问题、删掉、继续干活。但开发被另一个故障拉走了，忘了清理。这个 Pod 就这样运行了两周。

几天后，一个攻击者扫描集群时，通过一个配置不当的 NodePort 服务暴露的 Pod 元数据发现了这个 Pod。攻击者立刻意识到这是什么：一张通往集群的金色门票。

---

## 排查过程

### 第一步：确认逃逸

应急响应团队隔离了 `node-04`：

```bash
kubectl cordon node-04
```

然后检查调试 Pod：

```bash
kubectl exec -it debug-pod-nginx -n staging -- cat /host/etc/shadow
```

命令成功返回了宿主机的 shadow 文件。这意味着容器通过挂载的 `/host` 路径拥有完整的宿主机文件系统访问权限。

### 第二步：追溯突破路径

从特权容器内部逃逸到宿主机只需要一行命令：

```bash
# 挂载到宿主机命名空间
nsenter -t 1 -m -u -i -n -p -- bash
```

审计日志后来确认攻击者执行了这条命令，获得了宿主机上的 Root shell。紧接着：

```bash
# 在宿主机上
cat /etc/kubernetes/pki/ca.key   # 集群 CA 私钥
cat /etc/kubernetes/pki/admin.conf  # 管理员 kubeconfig

# 列出所有 Pod 和集群信息
kubectl get pods --all-namespaces
kubectl get secrets --all-namespaces
```

攻击者通过节点的 kubelet 凭证获得了 cluster-admin 级别的集群访问权限。

### 第三步：检查审计日志追踪横向移动

```bash
kubectl auth can-i --list --as=system:node:node-04
```

该节点的 kubelet 拥有过大的权限。攻击者利用它：

1. 窃取了集群 CA 证书和私钥
2. 创建了绑定了 cluster-admin 的新 ServiceAccount
3. 在另外 3 个节点上部署了挖矿程序

### 第四步：评估影响范围

```bash
# 检查从被攻陷节点访问了哪些 Secret
grep "node-04" /var/log/kubernetes/audit.log | grep "secrets" | grep "get"
```

15 个命名空间的数据库凭证、API 密钥、ServiceAccount token 可能已被泄露。

---

## 根因

多层防御全面失效：

1. **无 Pod 安全标准**：集群没有启用 Pod Security Admission 或 OPA/Gatekeeper，没有机制阻止创建特权容器
2. **无容器运行时安全**：没有部署运行时安全方案（Falco、AppArmor、seccomp），逃逸行为两周未被发现
3. **调试 Pod 无人清理**：没有策略或自动化机制清理临时调试资源
4. **节点凭证权限过大**：Kubelet 凭证拥有超出节点实际需求的 RBAC 权限

---

## 解决方案

### 紧急处置

```bash
# 封闭并驱逐被攻陷节点
kubectl cordon node-04
kubectl drain node-04 --ignore-daemonsets --delete-emptydir-data

# 删除调试 Pod
kubectl delete pod debug-pod-nginx -n staging

# 轮换集群 CA 和所有节点凭证
# (在控制平面执行)
mv /etc/kubernetes/pki/ca.{key,key.bak}
mv /etc/kubernetes/pki/ca.{crt,crt.bak}
kubeadm init phase upload-certs --upload-certs

# 重新构建被攻陷节点
kubectl delete node node-04
```

### 轮换所有被泄露的凭证

```bash
# 识别从 node-04 被访问的 Secret
# 然后逐个轮换（数据库密码、API 密钥、ServiceAccount token）
kubectl delete secret --all-namespaces -l app=critical
# 强制 Pod 重启以加载新凭证
kubectl delete pod --all-namespaces --field-selector spec.nodeName=node-04
```

### 预防措施

1. **Pod Security Admission (PSA)**：在命名空间级别强制执行 `restricted` 配置

```yaml
apiVersion: v1
kind: Namespace
metadata:
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
  name: production
```

2. **Falco 运行时安全**：部署 Falco 检测特权容器创建和宿主机挂载

```yaml
# Falco 规则：检测特权容器
- rule: Privileged Container Created
  desc: 检测特权容器的创建
  condition: container.privileged=true
  output: "检测到特权容器启动 (user=%user.name container=%container.name)"
  priority: CRITICAL
  tags: [container, security]
```

3. **OPA/Gatekeeper 策略**：在准入阶段拦截特权容器

```yaml
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sBlockPrivileged
metadata:
  name: block-privileged-containers
spec:
  match:
    kinds:
      - apiGroups: [""]
        kinds: ["Pod"]
  parameters:
    enabled: true
```

4. **临时 Pod 生命周期策略**：所有 `privileged: true` 的 Pod 必须带有 TTL 和所属人标签

5. **Node Restriction RBAC**：限制 kubelet 权限仅为其节点所需的最小集

## 经验教训

- **特权容器不是调试工具，而是宿主机级别的 Root 后门**：永远不要在非完全隔离的环境中使用 `privileged: true`。使用 `kubectl debug --ephemeral` 临时容器替代
- **Pod Security Admission 应该在集群部署第一天就启用**：事后补救意味着要清理大量遗留违规
- **审计所有 ServiceAccount 和节点凭证**：集群中的每个身份都应该每季度审查一次
- **运行时安全不是可选项**：签名扫描捕获已知恶意软件，但 Falco 等运行时工具捕获未知威胁——比如容器内的 `nsenter` 逃逸
- **调试 Pod 必须有策略的临时化**：使用 `kubectl debug --ephemeral` 创建临时容器，不留下持久的特权提升路径

---

## 总结

攻击链路：

```
开发人员创建带 privileged 权限和宿主机挂载的调试 Pod
→ Pod 运行了两周未被清理
→ 攻击者通过暴露的 NodePort 发现该 Pod
→ nsenter 逃逸到宿主机
→ 宿主机 CA 和 kubeconfig 被窃取
→ 全集群横向移动
→ 3 个额外节点被部署挖矿程序
→ 4 小时应急响应、凭证轮换、节点重建
```

根本修复：Pod Security Admission + Falco 运行时安全。这个特权提升路径非常经典——只是没有人设防。在有人走通之前关上门。
