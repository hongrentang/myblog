# TCP 端口耗尽排查实录——从 "Cannot assign requested address" 到 TIME_WAIT 堆积

## 你遇到过吗

凌晨 1 点 47 分，告警群炸了。

"支付回调推送失败率 78%"——这个数字让我直接从床上弹起来。

快速翻了翻日志：
- 服务 A（Python/Gunicorn）负责接收支付回调并转发到内部结算服务 B
- 日志里出现大量 `OSError: [Errno 99] Cannot assign requested address`
- 不是偶发，是持续报错

第一反应：完蛋，目标服务挂了？还是网络不通？

## 排查过程

### 错误尝试 1：怀疑目标服务 B 宕机

先确认目标端是不是还活着。登录机器，直接 curl：

```bash
curl -v http://10.0.0.50:8080/health
```

```
*   Trying 10.0.0.50:8080...
* Connected to 10.0.0.50 (10.0.0.50) port 8080 (#0)
> GET /health HTTP/1.1
> Host: 10.0.0.50:8080
> User-Agent: curl/7.68.0
> Accept: */*
>
* Mark bundle as not-in-connection 0
< HTTP/1.1 200 OK
< ...
```

健康检查正常，服务 B 在跑。

试了几次都正常。那问题不是在目标端。

### 错误尝试 2：怀疑 DNS 解析异常

看了一眼代码逻辑——服务 A 通过域名调用服务 B。会不会 DNS 解析挂了，拿到错误的地址？

```bash
dig +short payment-internal.svc.cluster.local
```

```
10.0.0.50
```

解析正常，IP 是对的。再用短域名试试：

```bash
dig +short payment-internal
```

```
10.0.0.50
```

也没有问题。那 DNS 不是根因。

**踩坑点**：这个排查花了我差不多 10 分钟。直觉让我先查目标端和 DNS，因为"连接不上"通常就这两个原因。但这次情况完全不同——不是连不上，是**没端口可用来连**。这就像你要打电话，但手机显示"没有可用的 SIM 卡"——对方的号码没问题，信号也没问题，是你自己没资源拨出去了。

### 错误尝试 3：怀疑连接池/线程池耗尽

仔细看日志，发现错误不是"connection refused"（拒绝连接），而是"Cannot assign requested address"。直觉告诉我跟端口有关。

先用 `ss` 看了下连接概况：

```bash
ss -s
```

```
Total: 40231 (kernel)
TCP:   22340 (estab 89, closed 22192, timewait 22101, ...)
```

22101 个 TIME_WAIT？？这个数字不对劲。一台机器上同时有两万多个连接处于 TIME_WAIT 状态。

```bash
# 看看具体是到哪的
ss -tan | awk '{print $4,$5}' | sort | uniq -c | sort -rn | head -10
```

```
21084 10.0.0.10:45231 10.0.0.50:8080
  312 10.0.0.10:45232 10.0.0.50:8080
  298 10.0.0.10:45233 10.0.0.50:8080
  ...
```

基本全是从本机（10.0.0.10）发往服务 B（10.0.0.50:8080）的连接。而且源端口都不一样——这很关键，说明每次请求都在新建连接。

### 关键发现：ephemeral port 耗尽

Linux 上，客户端发起 TCP 连接时，内核会给你分配一个临时端口（ephemeral port）。默认范围：

```bash
cat /proc/sys/net/ipv4/ip_local_port_range
```

```
32768 60999
```

可用的临时端口数量 = 60999 - 32768 = **28231** 个。

现在有 22101 个 TIME_WAIT 连接占着端口不放（TIME_WAIT 默认持续 60 秒），再加上正常 ESTABLISHED 的连接，可用端口已经被吃光了。

```bash
# 验证：看还有多少端口可用
cat /proc/sys/net/ipv4/ip_local_port_range
echo "可用端口: $((60999 - 32768 - $(ss -tan state time-wait | wc -l)))"
```

结果是负数——根本没端口用了。

确认一下进程到底在做什么：

```bash
# 看进程状态
strace -e trace=network -p $(pgrep -f gunicorn) 2>&1 | head -20
```

```
connect(33, {sa_family=AF_INET, sin_port=htons(8080), sin_addr=inet_addr("10.0.0.50")}, 16) = -1 EADDRNOTAVAIL (Cannot assign requested address)
```

实锤了。`connect()` 系统调用返回 `EADDRNOTAVAIL`——内核找不到可用的临时端口来发起新连接。

### 为什么端口会被吃光

看代码。

服务 A 是用 `requests` 库做 HTTP 调用。原来的写法是这样的：

```python
import requests

def forward_payment(data):
    resp = requests.post("http://payment-internal:8080/orders", json=data)
    return resp.json()
```

每次调用 `forward_payment` 都新建一个 TCP 连接。请求完成后连接关闭，进入 TIME_WAIT。

在高并发场景下（支付回调峰值每秒上百笔），每笔产生一个新连接。TIME_WAIT 要等 60 秒才释放。60 秒 × 100 qps = **6000 个连接**同时卡在 TIME_WAIT。

理论上 28231 个端口够撑一会儿，但问题是——Gunicorn 有多个 worker，每个 worker 都在并发处理请求。峰值时一秒内可能创建数千个连接，端口号虽然多，但 TIME_WAIT 积累速度远超释放速度。

用 `ss -tan` 看时间分布：

```bash
ss -tan state time-wait | awk '{print $4}' | cut -d: -f2 | sort -n | head -5
```

```
32768
32769
32800
32850
...
```

端口从 32768 开始几乎连续分配，已经用到了 60000 附近——说明端口池已经被完整扫过一遍以上。

## 根因分析

| 层面 | 原因 |
|------|------|
| 直接原因 | 每个 HTTP 请求创建新 TCP 连接，高并发下 TIME_WAIT 堆积耗尽临时端口 |
| 代码缺陷 | 使用 `requests` 裸调用，未复用连接（没有 Session / connection pool） |
| 触发条件 | 支付回调高峰流量，秒级数百并发 |
| 为什么不影响其他流量 | 只有服务 A → 服务 B 这一跳有问题，因为只有这个方向使用了短连接模式 |

一句话总结：**代码每次请求都建新连接，TIME_WAIT 堆积撑爆了内核临时端口池。**

## 解决方案

### 紧急止血：扩大端口范围（临时）

先让服务恢复，别让告警继续响：

```bash
sysctl -w net.ipv4.ip_local_port_range="1024 65535"
```

修改 `/etc/sysctl.conf` 持久化：

```
net.ipv4.ip_local_port_range = 1024 65535
```

可用端口从 28231 扩大到 64511，暂时够用。

```bash
sysctl -p
```

同时调小 TIME_WAIT 持续时间（仅临时救急）：

```bash
sysctl -w net.ipv4.tcp_fin_timeout=15
```

**注意**：`tcp_fin_timeout` 控制的是 FIN-WAIT-2 的超时，不是直接控制 TIME_WAIT。真正的 TIME_WAIT 在 Linux 上是写死的 60 秒（基于 MSL=30s × 2）。`tcp_tw_reuse` 更关键：

```bash
sysctl -w net.ipv4.tcp_tw_reuse=1
```

`tcp_tw_reuse` 允许内核在分配新端口时，如果时间戳允许，直接复用 TIME_WAIT 状态的端口。**这只对出站连接有效**（client 侧），刚好适合我们的场景。

### 根本修复：连接池（代码改）

扩大端口是治标，不改代码流量再涨一样挂。正确做法是用 `requests.Session`：

```python
import requests
from urllib3.util.retry import Retry
from requests.adapters import HTTPAdapter

# 创建带连接池的 session
session = requests.Session()

# 配置连接池和重试
adapter = HTTPAdapter(
    pool_connections=50,     # 连接池大小
    pool_maxsize=200,        # 最大连接数
    pool_block=True,          # 连接池满时阻塞而非失败
    max_retries=Retry(
        total=2,
        backoff_factor=0.5,
        status_forcelist=[502, 503, 504]
    )
)
session.mount("http://", adapter)
session.mount("https://", adapter)

def forward_payment(data):
    # session 会自动复用连接池中的连接
    resp = session.post("http://payment-internal:8080/orders", json=data, timeout=5)
    return resp.json()
```

**为什么连接池有效**：

| 机制 | 作用 |
|------|------|
| 连接复用 | 请求走同一个 TCP 连接，避免反复三次握手四次挥手 |
| 减少 TIME_WAIT | 连接不关闭就不会产生 TIME_WAIT |
| 降低延迟 | 复用连接省掉了 TCP 握手和 TLS 握手的 RTT |
| 避免端口耗尽 | 几十个长连接足够承载数百 QPS |

部署新代码后验证：

```bash
# 部署后 5 分钟查看连接状态
ss -tan state time-wait | wc -l
```

```
234
```

从两万多降到两百多。

```bash
ss -tan | grep 8080
```

```
ESTAB  10.0.0.10:45231  10.0.0.50:8080
ESTAB  10.0.0.10:45232  10.0.0.50:8080
ESTAB  10.0.0.10:45233  10.0.0.50:8080
ESTAB  10.0.0.10:45234  10.0.0.50:8080
...
```

全部是 ESTAB 状态，没有 TIME_WAIT。连接被复用了。

### 验证恢复

```bash
# 1. 确认错误日志消失
grep "Cannot assign requested address" /var/log/app/error.log
# 没有输出 = 没再出现

# 2. 确认端口池使用正常
ss -tan state time-wait | wc -l
# 应该远低于 28231

# 3. 支付成功率监控
# 告警群的 78% 失败率应该降到 0.1% 以下（网络抖动导致的极少数失败）

# 4. 压力测试
ab -n 1000 -c 100 http://localhost:8080/call-b
# 无错误 = 修复确认
```

✅ **恢复确认**：
- 日志没有再出现 `EADDRNOTAVAIL`
- TIME_WAIT 从 22101 降到 234
- 支付回调成功率回到 99.9%+

### 长期预防

```bash
# 监控 TCP 连接状态
# Prometheus node_exporter 有 node_netstat_Tcp_TimeWait 指标
# 或者用脚本定期采集
ss -tan state time-wait | wc -l
# TIME_WAIT > 10000 触发告警

# 代码规范
# - 所有 HTTP 调用必须使用 Session/连接池
# - Code Review 时关注 requests 调用方式
# - 微服务间调用考虑 gRPC（自带连接复用）

# 内核参数一起固化
cat >> /etc/sysctl.d/99-network-tuning.conf << 'EOF'
net.ipv4.ip_local_port_range = 1024 65535
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_fin_timeout = 15
net.core.somaxconn = 4096
EOF

sysctl --system
```

## 事后看，如果重来一次我应该怎么做

**第一步就该看 `ss -s`。**

不是查 DNS，不是 curl 后端，甚至不是看日志文件。直接看系统级连接状态，"Total: 40231, TIME_WAIT: 22101" 这个数据一出来，方向直接就定了。

很多网络故障的排查都有这个特点——你以为是对面出了问题，但其实是你自己的机器"没资源"跟对面通信了。端口耗尽、连接池占满、文件描述符用光，都属于这一类。这类问题的特点是**只在压力下出现**，低负载时怎么测都是正常的。

## 教训总结

1. **"Cannot assign requested address" 不是权限问题**。第一次看到这个错，我甚至去查了 selinux 和 capabilities。实际上 `EADDRNOTAVAIL` 的意思是"内核没有可用端口了"——你被自己耗尽了。

2. **`requests` 裸调用是反模式**。每一次 `requests.get()` 都在创建新连接。生产环境必须用 `Session`。这不是性能优化，是正确性问题——不用连接池的话，高并发下端口一定会耗尽，只是时间问题。

3. **TIME_WAIT 不是 bug，但堆积是。** TCP 的 TIME_WAIT 是必要的（保证对端收到最后的 ACK），正常场景下个位数到几十个 TIME_WAIT 完全正常。但如果一个目标地址上有几千上万个 TIME_WAIT，那肯定是你代码里没复用连接。

4. **压测要覆盖连接层。** 功能测试不会暴露端口耗尽问题，因为 QPS 不够。上线前的压测至少要看：TIME_WAIT 数量、本地端口使用量、连接建立速率。这三个指标异常一个，上线后必出事故。
