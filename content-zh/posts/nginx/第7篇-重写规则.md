## Location 匹配规则

`location` 决定了请求 URI 被哪个配置块处理，是 Nginx 最核心也是最容易搞混的指令之一。

### 匹配优先级

```nginx
location = /exact {        # 1. 精确匹配（最高优先级）
    ...
}

location ^~ /static/ {     # 2. 优先前缀匹配
    ...
}

location ~ \.php$ {        # 3. 正则匹配（大小写敏感）
    ...
}

location ~* \.(jpg)$ {     # 4. 正则匹配（大小写不敏感）
    ...
}

location / {               # 5. 通用前缀匹配（最低优先级）
    ...
}
```

**匹配流程**：

```
请求 /logo.jpg
1. 先匹配前缀 location —— 找到最长的匹配
2. 如果是 ^~ 匹配 → 直接使用，跳过正则
3. 否则按顺序检查正则 location
4. 如果正则匹配 → 使用正则 location
5. 如果正则都不匹配 → 使用第1步找到的最长前缀匹配
```

### 完整的优先级示例

```nginx
server {
    root /var/www/html;

    location = / {                    # 精确匹配 / → /var/www/html/index.html
        try_files /index.html =404;
    }

    location = /favicon.ico {         # 精确匹配
        log_not_found off;
        access_log off;
    }

    location ^~ /static/ {            # 优先前缀
        root /var/www;
        expires 30d;
    }

    location ~ \.php$ {               # 正则匹配 PHP
        fastcgi_pass unix:/var/run/php-fpm.sock;
        include fastcgi_params;
    }

    location ~* \.(jpg|png|gif)$ {    # 正则匹配图片
        expires 7d;
    }

    location / {                      # 兜底
        try_files $uri $uri/ /index.php?$query_string;
    }
}
```

### location 嵌套

Nginx 不支持 location 嵌套，但可以通过一些技巧模拟：

```nginx
# 方法1：在 location 中用 if（不推荐嵌套太多）
location /admin {
    # /admin 下的规则
    ...
}

# 方法2：使用 include 复用配置
location /api/ {
    include snippets/cors.conf;
    proxy_pass http://api_backend;
}

location /api/v2/ {
    include snippets/cors.conf;
    proxy_pass http://api_v2_backend;
}
```

## rewrite 指令

`rewrite` 用于改写请求 URI，语法：

```nginx
rewrite regex replacement [flag];
```

### 基本用法

```nginx
# 将 /article/123 重写为 /article?id=123
rewrite ^/article/(\d+)$ /article?id=$1 last;

# 将 /page/about 重写为 /about.html
rewrite ^/page/(.*)$ /$1.html permanent;
```

### 四种 flag

| flag | 行为 | 使用场景 |
|------|------|---------|
| `last` | 停止当前 location，重新匹配 location | 内部重写 |
| `break` | 停止当前 location，不重新匹配 | 单次重写 |
| `redirect` | 返回 302 临时重定向 | 临时跳转 |
| `permanent` | 返回 301 永久重定向 | 永久跳转 |

### last vs break 的区别

```nginx
location /a/ {
    rewrite ^/a/(.*) /b/$1 last;    # → 重新匹配 location
    # 下一行不会被执行
    return 200 "from a";
}

location /b/ {
    rewrite ^/b/(.*) /c/$1 break;   # → 不重新匹配，继续当前块
    # break 之后的指令仍会执行
    return 200 "from b";
}

location /c/ {
    return 200 "from c";
}
```

如果想看实际效果的读者，可以在本地配置测试。理解 `last` 和 `break` 的关键差异在于：`last` 会重新走一遍 location 匹配，而 `break` 不会。

## try_files 指令

`try_files` 按顺序尝试文件，常用在单页应用和 WordPress 中：

```nginx
# SPA 单页应用：如果文件存在则返回，不存在则返回 index.html
location / {
    try_files $uri $uri/ /index.html;
}

# 带参数传递
location / {
    try_files $uri $uri/ /index.php?$query_string;
}

# 自定义错误
location / {
    try_files $uri $uri/ /error.html =404;
}
```

执行顺序：先尝试 `$uri`（请求路径），再尝试 `$uri/`（请求路径作为目录），最后回退到 `/index.html`。

## return 指令

```nginx
location /old-path {
    return 301 /new-path;
}

location /gone {
    return 410;  # 资源已永久删除
}

location /api {
    return 200 "OK";  # 直接返回文本
}
```

常见 HTTP 状态码：

| 状态码 | 含义 | 使用场景 |
|--------|------|---------|
| 301 | 永久重定向 | 域名变更、SEO |
| 302 | 临时重定向 | 临时维护 |
| 307 | 临时重定向（保持请求方法）| POST 重定向 |
| 308 | 永久重定向（保持请求方法）| POST 永久重定向 |
| 404 | 未找到 | 资源不存在 |
| 410 | 已删除 | 资源永久删除 |
| 444 | 关闭连接（Nginx 特有）| 拒绝恶意请求 |

## 实战场景

### 场景一：HTTP 跳转 HTTPS

```nginx
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$server_name$request_uri;
}
```

### 场景二：强制 www 前缀

```nginx
server {
    listen 80;
    server_name example.com;
    return 301 https://www.example.com$request_uri;
}

server {
    listen 443 ssl;
    server_name example.com;
    return 301 https://www.example.com$request_uri;
}

server {
    listen 443 ssl;
    server_name www.example.com;
    # 真正的站点配置
}
```

### 场景三：移除 index.html

```nginx
# 如果请求以 index.html 结尾，去掉它
if ($request_uri ~ ^/(.*)index\.html$) {
    return 301 /$1;
}
```

### 场景四：移动端跳转

```nginx
location / {
    if ($http_user_agent ~* "(android|iphone|ipad)") {
        rewrite ^(.*)$ /mobile$1 last;
    }
}

location /mobile {
    root /var/www/mobile;
}
```

### 场景五：维护页面

```nginx
location / {
    if (-f $document_root/maintenance.html) {
        return 503;
    }
}

error_page 503 @maintenance;
location @maintenance {
    rewrite ^(.*)$ /maintenance.html break;
}
```

放一个 `maintenance.html` 到根目录，所有请求自动跳转维护页面，删除文件即恢复。

## if 指令的陷阱

`if` 在 location 中使用时要非常小心，**很多场景下 if 的行为和预期不一样**。

### 公认的安全用法

```nginx
# ✅ 只使用 return 或 rewrite ... last
if ($scheme != "https") {
    return 301 https://$server_name$request_uri;
}

if ($request_method = POST) {
    return 405;
}

if ($http_user_agent ~* (curl|wget)) {
    return 403;
}

if ($request_uri ~* "\.(bak|old|swp)$") {
    return 404;
}
```

### 不安全的用法（不要这样写）

```nginx
# ❌ 不要用 if 做 try_files 的事情
if (-f $document_root/cache/$uri) {
    rewrite ^ /cache/$uri break;
}

# ❌ 不要在 if 里用 proxy_pass（行为不可预测）
if ($uri ~* ^/api/) {
    proxy_pass http://api_backend;
}
```

**黄金法则**：`if` 里尽量只放 `return` 或 `rewrite ... last`。

## 调试重写规则

```nginx
location /debug {
    # 查看 rewrite 过程日志
    rewrite_log on;
    return 200 "debug location\n";
}
```

开启 `rewrite_log` 后，在 `error_log` 中可以看到详细的 rewrite 过程：

```nginx
error_log /var/log/nginx/error.log notice;
```

日志输出示例：

```
2025/01/15 10:00:00 [notice] 1234#1234: *1 "^/article/(\d+)" matches "/article/42", client: 1.2.3.4
2025/01/15 10:00:00 [notice] 1234#1234: *1 rewritten data: "/article?id=42", args: ""
```

## 小结

location 匹配和 rewrite 是 Nginx 配置中最复杂也最强大的部分。掌握优先级规则和 if 的安全用法，你就能写出既灵活又不会出问题的配置。
