## 为什么需要负载均衡？

当单台服务器扛不住流量时，就需要多台服务器分担压力。负载均衡的作用就是**把请求合理地分发到多台后端服务器**上。

```
                    ┌─ Server A (10.0.0.1:8080)
用户 → Nginx ────  ├─ Server B (10.0.0.2:8080)
                    ├─ Server C (10.0.0.3:8080)
                    └─ Server D (backup)
```

---

## upstream 配置

负载均衡的核心是 `upstream` 块：

```nginx
upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}

server {
    listen 80;
    location / {
        proxy_pass http://backend;
    }
}
```

## 负载均衡算法

### 1. 轮询（Round Robin，默认）

```nginx
upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}
```

请求按顺序轮流分配给每台服务器，适合各服务器配置相同的场景。

### 2. 加权轮询（Weighted）

```nginx
upstream backend {
    server 10.0.0.1:8080 weight=3;   # 处理 3/6 的请求
    server 10.0.0.2:8080 weight=2;   # 处理 2/6 的请求
    server 10.0.0.3:8080 weight=1;   # 处理 1/6 的请求
}
```

权重越高流量越多，适合服务器性能不一的情况。

### 3. IP Hash

```nginx
upstream backend {
    ip_hash;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}
```

**同一客户端 IP 始终分配到同一台服务器**，适合需要维持 Session 的场景。

注意事项：
- 如果某台服务器挂了，该服务器上的 IP 会重新分配到其他节点
- 客户端如果通过代理访问，IP Hash 可能失效（因为 Nginx 看到的都是代理 IP）

### 4. 最少连接（Least Connections）

```nginx
upstream backend {
    least_conn;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}
```

请求发给当前活跃连接数最少的服务器，适合请求处理时间差异大的场景。

### 5. 随机（Random）

```nginx
upstream backend {
    random;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}
```

Nginx 1.15.7+ 支持，从可用服务器中随机选择。

### 6. 一致性 Hash

```nginx
upstream backend {
    hash $request_uri consistent;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
```

根据自定义 key（如 URI、Cookie）进行 hash 分配，`consistent` 参数启用一致性哈希算法，增减服务器时影响面最小。

## 服务器参数

```nginx
upstream backend {
    # 基本定义
    server 10.0.0.1:8080;

    # 权重
    server 10.0.0.2:8080 weight=5;

    # 最大失败次数和失败超时
    server 10.0.0.3:8080 max_fails=3 fail_timeout=30s;

    # 最大连接数（配合排队）
    server 10.0.0.4:8080 max_conns=100;

    # 慢启动（上线后逐步增加流量）
    server 10.0.0.5:8080 slow_start=30s;

    # 备机（其他服务器都挂了才启用）
    server 10.0.0.6:8080 backup;

    # 标记为已下线（不参与负载，也不报错）
    server 10.0.0.7:8080 down;
}
```

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `weight` | 权重 | 1 |
| `max_fails` | 最大失败次数，超过后标记为不可用 | 1 |
| `fail_timeout` | 失败超时时间 | 10s |
| `max_conns` | 最大并发连接数 | 0（不限）|
| `slow_start` | 慢启动时间 | 0（不启用）|
| `backup` | 标记为备机 | - |
| `down` | 标记为永久下线 | - |

## 健康检查

### 被动健康检查（Nginx 自带）

Nginx 开源版只支持被动健康检查——通过实际请求的响应来判断服务器是否存活：

```nginx
upstream backend {
    server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 max_fails=3 fail_timeout=30s;
}
```

连续 `max_fails` 次失败（连接超时、HTTP 5xx 等），在 `fail_timeout` 内不再向该服务器转发请求。

### 主动健康检查（Nginx Plus 或第三方模块）

Nginx Plus 支持主动健康检查：

```nginx
upstream backend {
    zone backend 64k;

    server 10.0.0.1:8080;
    server 10.0.0.2:8080;

    health_check interval=5s fails=3 passes=2 uri=/health;
}
```

开源版可以使用 `nginx_upstream_check_module` 第三方模块实现类似功能。

## 重试机制

```nginx
location / {
    proxy_pass http://backend;
    proxy_next_upstream error timeout http_500 http_502 http_503;
    proxy_next_upstream_tries 3;
    proxy_next_upstream_timeout 10s;
}
```

上游服务器返回指定的错误码时，Nginx 会尝试下一个节点。

```nginx
# 非幂等请求（POST、PUT）默认不重试
proxy_next_upstream error timeout;
proxy_next_uprustream_timeout 0;
```

**注意**：POST 等非幂等请求要谨慎启用重试，避免重复下单等问题。

## Session 保持

### 方案一：IP Hash

```nginx
upstream backend {
    ip_hash;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
```

### 方案二：Cookie 定向

```nginx
upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    sticky cookie srv_id expires=1h domain=.example.com path=/;
}
```

需要 Nginx Plus 或 `nginx-sticky-module` 第三方模块。

### 方案三：共享 Session（推荐）

不依赖负载均衡策略，将 Session 存入 Redis/Memcached：

```python
# 伪代码
session_store = RedisSessionStore(host='redis-cluster.example.com')
```

这是最 scalable 的方案，后端扩缩容对前端完全透明。

## 长连接

代理时保持与后端的长连接可以显著提升性能：

```nginx
upstream backend {
    server 10.0.0.1:8080;
    keepalive 32;                       # 最大空闲连接数
    keepalive_requests 100;             # 每个连接最大请求数
    keepalive_timeout 60s;              # 空闲超时
}

server {
    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

**关键点**：
- 必须设置 `proxy_http_version 1.1`
- 必须清空 `Connection` 头
- `keepalive` 不是限制总连接数，而是限制**空闲连接**数

## 完整示例

```nginx
upstream api_backend {
    least_conn;
    keepalive 32;

    server api1.example.com:8080 weight=5 max_fails=3 fail_timeout=30s;
    server api2.example.com:8080 weight=5 max_fails=3 fail_timeout=30s;
    server api3.example.com:8080 weight=3 max_fails=3 fail_timeout=30s;
    server api4.example.com:8080 backup;
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://api_backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        proxy_next_upstream error timeout http_500;
        proxy_next_upstream_tries 3;

        proxy_connect_timeout 5s;
        proxy_read_timeout 30s;
    }
}
```
